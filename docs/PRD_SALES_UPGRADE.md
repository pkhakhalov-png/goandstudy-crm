## 1. Что есть сейчас — проверенные факты

### 1.1. Что работает

| Что | Состояние |
|---|---|
| Приём заявок | Три канала: квиз на сайте (`/api/book/lead`), Telegram-бот групп, ручное создание. Всё падает в `deals` через `lib/booking/create.ts`. |
| Воронка | 14 этапов в `pipeline_stages`, карточка сделки с вкладками «главное / активность / файлы / чат / задачи». |
| Чат с клиентом | Telegram + Wazzup внутри карточки, 24 513 сообщений в базе, real-time через Supabase. |
| Кабинет РОПа | `/rop/*` — застрявшие, время ответа, конверсии, планы, нагрузка. Пороги настраиваются в `rop_settings`. |
| Назначение продажника | Round-robin по расписанию, зазор 60 минут между консультациями. |
| Очередь фоновых задач | `seo.jobs` + воркер `/api/seo/tick` по pg_cron. Аренда задач, повторы, учёт стоимости моделей — уже есть. |
| Распознавание речи | `lib/finance/speech.ts` — Gemini, работает на голосовых финансового бота. |

Фундамент сильный. Это важно: почти всё ниже — достройка, а не переписывание.

### 1.2. Чего нет и что из-за этого не видно

**Звонка в системе не существует.** Ни одной записи, транскрипта, оценки. `deal_activities` знает три типа: `message` (911 из последних 1000), `system` (51), `stage_change` (38). Звонок — главное событие продажи — не оставляет в CRM следа вообще. Всё, что от него остаётся, — текст в `custom_fields.consultation_notes`, заполненный вручную у 227 сделок.

**Воронка разошлась с фактом продаж вчетверо.** За 90 дней заведено 24 клиента (реальные продажи), а в успешных этапах воронки суммарно 6 сделок, из них в «Первичная продажа» — ноль. Продажу оформляют через `/sales/new`, сделку в воронке не двигают. Следствие: любая конверсия, которую сейчас считает `/rop/conversions`, считает не то.

**Воронка — кладбище.** 1041 сделка из 1111 (94 %) без движения больше 5 дней. Панель «Застрявшие» показывает почти всю базу — то есть не показывает ничего.

**Итог консультации не фиксируется.** Из 157 прошедших броней 35 (22 %) до сих пор в статусе `confirmed` — никто не отметил, состоялась ли встреча. Показатель «дошёл / не дошёл» посчитать нельзя.

**Задачи мертвы.** 336 открытых задач, из них 333 просрочены. Механизм есть, доверия к нему нет — а значит, «следующий шаг» в CRM не живёт.

**Цикл сделки не измеряется.** `closed_at` не заполнен ни у одной сделки из 1111.

## 2. Цель и рамки

### 2.1. Цель

Сделать так, чтобы:

1. **Каждый разговор с клиентом попадал в CRM** — запись, расшифровка, разбор по чек-листу, следующий шаг.
2. **Руководитель видел качество, а не только количество** — по каждому продажнику, по каждому пункту чек-листа, за 5 минут утром.
3. **Воронка перестала врать** — успешный этап привязан к факту оплаты, исход консультации обязателен, цикл сделки измеряется.
4. **«Ожидание» стало рабочей очередью** — система сама предлагает, кого и с каким поводом вернуть, и с чем прийти к оплатившим.

### 2.2. Что НЕ делаем в этой версии

- Не меняем интерфейс продажника радикально — добавляем, не ломаем.
- Не переносим телефонию. Если звонки идут не только в Zoom, а ещё и по телефону, это отдельный блок (см. раздел 13, вопрос 3).
- Не строим свою STT-модель. Используем внешнюю, как уже делаем для голосовых.
- Не делаем автоматическую отправку сообщений клиенту от лица ИИ. ИИ готовит черновик — отправляет человек.
- Не трогаем кабинеты куратора и клиента.

### 2.3. Принцип, которому подчинено всё остальное

**Оценка звонка — это подсказка, а не приговор.** Как только по оценке ИИ начнут депремировать, продажники начнут говорить под запись, а не продавать. Это наблюдение записано прямо в гайде конкурента и совпадает с нашим опытом: система показывает РОПу, куда копать, решение принимает человек. Отсюда — в интерфейсе нет слова «рейтинг наказания», а есть «что тренируем на этой неделе».

## 3. Блок 0 — Фундамент: воронка должна перестать врать

**Без этого блока остальные считают ерунду.** Он самый дешёвый и самый важный.

### 3.1. Успешный этап привязывается к оплате

Сейчас продажа оформляется в `/sales/new` (создаётся `client` + `payments`), а сделка в воронке остаётся где была.

Делаем (**решение принято 24.09.2026: автоматический перевод, не кнопка-подсказка**): в `app/sales/new/actions.ts` после успешного создания клиента — если продажник пришёл из карточки сделки (или сделка находится по нормализованному телефону), сделка автоматически переводится в «Оплата услуг», проставляется `closed_at`, `client_id`, `budget` = сумма договора, и в ленту падает системная запись с именем того, кто оформил.

Перевод виден в ленте и откатывается вручную, как любой другой переход этапа. Флаг `funnel_autoclose` выключает поведение целиком.

Обратный ход тоже: возврат (`payments.num = -1`) снимает `closed_at`.

### 3.2. Исход консультации обязателен

Новое поле `bookings.outcome` (`held` / `no_show` / `rescheduled` / `cancelled`) + `outcome_at` + `outcome_by`.

- Через 2 часа после конца слота консультация попадает продажнику в блок «отметьте исход» на `/sales`.
- Пока не отмечено — счётчик висит и виден РОПу.
- Если по этой сделке появился разбор звонка (блок 1), исход `held` проставляется автоматически.

Задним числом 35 подвисших броней не трогаем: помечаем `outcome = unknown`, чтобы статистика не врала задним числом.

### 3.3. Чистка застрявших

94 % сделок «застряли» — это шум. Меняем определение застревания на честное:

- Считаем от **последней активности человека** (`deal_activities` с `user_id`), а не от `deals.updated_at` (его двигает любой фоновый апдейт).
- Считаем только по этапам, где движение вообще ожидается (`active`), а «Догрев» / «На будущее» выводим отдельной вкладкой с собственным сроком возврата.
- «НЕ ЦЕЛЕВЫЕ» (210) и «Релокац» (297) в метрики продаж не попадают вообще — это отдельные потоки.

Ожидаемый результат: список застрявших схлопывается с 1041 до десятков — и им снова можно пользоваться.

### 3.4. Задачи оживают — причина оказалась технической

В первой редакции ПРД здесь стояло «задачи мертвы, механизм есть, доверия нет».
При разборе кода выяснилось, что дело не в дисциплине, а в баге.

Задача «клиент написал — надо ответить» заводится автоматически на входящее
сообщение: и в Telegram, и в Wazzup. **Закрывалась она ровно в одном месте** —
в вебхуке Wazzup, когда приходило эхо исходящего. У Telegram такой ветки не
было вовсе, а отправка из карточки сделки не закрывала задачу ни в одном
канале.

Telegram — основной канал: в выборке из 1000 последних сообщений телеграмными
оказались все 1000. То есть почти каждое входящее оставляло после себя задачу,
закрыть которую могла только рука человека, и никто, разумеется, не закрывал.
Отсюда 336 открытых задач, из них 333 просроченных, самая старая — от 21 апреля.

**Вторая поломка из того же места.** Вебхук Telegram сохранял *все* сообщения
как `direction: 'incoming'` — включая ответы самого продажника, написанные
прямо в групповом чате. Следствия два: такие ответы заводили задачу «ответить
клиенту» на самого себя, а время ответа по групповым чатам не считалось вообще,
потому что исходящих в них по данным вебхука не существовало.

Что сделано:

- `lib/sales/reply-tasks.ts` — закрытие задачи вынесено в общий помощник и
  вызывается отовсюду, откуда уходит ответ: карточка сделки (обе ветки —
  TG-группа через Bot API и Wazzup), эхо Wazzup, ответ сотрудника в группе.
- Вебхук Telegram узнаёт своих по `users.telegram_username`: их сообщения
  пишутся как исходящие, задача не заводится, а открытая — закрывается.
  Username заполнен у 4 из 11 продажников; для остальных поведение прежнее,
  и заполнение поля чинит статистику по человеку сразу.
- `deal_tasks.closed_as` (`done` / `expired`) — чтобы автозакрытие брошенных не
  превратило 333 провала в 333 выполненные задачи.
- `public.expire_stale_tasks()` — закрывает просроченные больше
  `rop_settings.task_expire_days` (по умолчанию 14) как `expired`. Расписание
  включается отдельно, после проверки функции.

Накопленный долг — 278 задач старше 14 дней — закрывается одним вызовом этой
функции. Это видимое для продажников изменение, поэтому выполняется по
отдельному решению, а не заодно с выкаткой.

## 4. Блок 1 — Разговоры: Zoom, запись, расшифровка, разбор

Это ядро апгрейда.

### 4.1. Как разговор попадает в систему

Три пути, в порядке внедрения:

**Путь А — ручная загрузка (доступен сразу, ничего не требует).**
В карточке сделки — вкладка «Разговоры», кнопка «Загрузить запись». Продажник кидает файл из Zoom (или любой другой записи), выбирает тип (консультация / дожим / повторный), жмёт «разобрать». Дальше всё автоматически.

**Путь Б — автоматический из Zoom.** Тариф подтверждён: **Zoom Workplace Профессиональный** (15,99 €/пользователь в месяц). Облачная запись, API и вебхуки на нём есть — путь Б доступен.

Ключевое следствие тарифа: **встречу создаём мы, а не продажник вручную.** При создании брони (`lib/booking/create.ts`) дёргаем Zoom API `POST /users/{id}/meetings`, получаем `meeting_id` и `join_url`, кладём их в бронь и отдаём клиенту в подтверждении. Дальше сшивка становится точной, а не вероятностной:

```
booking.zoom_meeting_id  ←→  webhook payload.object.id
```

Угадывать по телефону и теме встречи не нужно вообще. Это заметно надёжнее, чем предполагалось до того, как стал известен тариф.

Поток:
1. Вебхук `recording.completed` приходит на `/api/zoom/webhook`.
2. Проверяем подпись Zoom (`x-zm-signature` + `zoom_webhook_signature_token`, по той же схеме, что уже сделана для Telegram и WordPress). Отдельно обрабатываем `endpoint.url_validation` — Zoom требует ответить на него при подключении.
3. По `payload.object.id` находим бронь и сделку.
4. Скачиваем запись по `download_token` (живёт 24 часа — скачиваем сразу, в очередь кладём уже наш файл).
5. Кладём в Supabase Storage, приватный бакет `call-recordings`.
6. Ставим задачу в очередь.
7. **Удаляем запись из облака Zoom** (`DELETE /meetings/{id}/recordings`) — см. 4.1.1.

Если встреча прошла вне брони (продажник запустил личную конференцию) — сшивка по хосту и времени, а не сошлось — в «Неопознанные разговоры» на `/rop/calls`, откуда привязывается в один клик.

#### 4.1.1. Место в облаке Zoom — это ограничение, о котором надо решить сразу

На Профессиональном даётся **5 ГБ на лицензию**. Консультация 45 минут:

| Формат записи | Размер | 5 ГБ хватит на |
|---|---|---|
| Видео + звук (MP4, 720p) | ~350–500 МБ | 10–14 консультаций |
| Только звук (M4A) | ~40–50 МБ | ~100 консультаций |

То есть при записи видео место кончится за две-три недели, и Zoom начнёт отказывать в записи молча — для продажника это будет выглядеть как «запись не включилась».

Отсюда два решения, оба обязательны:

1. **Пишем только звук.** В настройках облачной записи выключаем видеодорожки, оставляем `Audio only`. Нам нужен разговор, а не лицо — на разборе видео не используется, а стоит в 10 раз дороже по месту.
2. **Чистим Zoom после себя.** Как только файл лёг в Supabase Storage и запись в `call_recordings` получила статус `ingested` — удаляем её из облака Zoom. Хранилище Zoom перестаёт быть узким местом навсегда, а наш архив живёт по своему сроку (раздел 9.5). Удаление делается отдельным шагом очереди **после** подтверждённой записи в Storage, а не «за компанию» со скачиванием: потерять единственную копию из-за сбоя между двумя действиями нельзя.

Дополнительно включаем в настройках записи **«отдельная аудиодорожка на каждого участника»** — тогда роли в расшифровке известны точно, и модели не придётся их угадывать (см. 4.3). Наличие этой опции на нашем тарифе проверяем в настройках аккаунта на Э0; если её нет, роли определяет модель — это рабочий, хоть и чуть менее точный вариант.

**Путь В — телефония.** Вне рамок версии 1 (см. раздел 13).

### 4.2. Конвейер обработки

Новая дорожка (`lane`) в существующей очереди `seo.jobs`. Ничего нового строить не нужно — аренда задач, повторы, учёт стоимости моделей там уже работают.

```
call_ingest      → файл в Storage, длительность, участники
call_transcribe  → расшифровка с разделением ролей
call_analyze     → разбор по чек-листу, структурированный ответ
call_apply       → следующий шаг → задача, итог → лента сделки, оценка → дашборд
call_purge_zoom  → удаление записи из облака Zoom, когда наша копия подтверждена
```

Каждый шаг идемпотентен и падает независимо: если разбор не удался, расшифровка остаётся — и её уже можно читать.

### 4.3. Расшифровка

Берём Gemini, как в `lib/finance/speech.ts`, но через **Files API** вместо inline: у inline потолок 20 МБ и 3 минуты, а консультация идёт 40–60 минут. Files API принимает длинное аудио без нарезки — это важно, потому что на Vercel нет ffmpeg и резать файл нечем.

Разделение ролей: при пути Б, если включена отдельная дорожка на участника (см. 4.1.1), роли известны точно — продажник это хост, остальные клиент. При ручной загрузке и при общей дорожке роли определяет модель, и в карточке стоит пометка «роли определены автоматически», чтобы РОП знал, чему верить.

**Риск, который надо померить на первом же реальном звонке:** функция на Vercel живёт 300 секунд. Час аудио через Gemini укладывается ориентировочно в 60–120 с, но это оценка, а не замер. Если не уложимся — расшифровка уходит на отдельный воркер с более длинным бюджетом. Решение принимаем после замера, а не заранее.

### 4.4. Разбор по чек-листу

Чек-лист хранится в базе (`call_checklists` + `call_checklist_items`), а не в коде — РОП правит его сам в `/rop/settings`. Стартовый набор под наш продукт, 8 пунктов:

| № | Пункт | Что проверяем |
|---|---|---|
| 1 | Контакт и цель | Представился, обозначил, зачем встреча и сколько она займёт |
| 2 | Квалификация | Кто принимает решение (студент / родитель), страна, уровень, сроки, бюджетные рамки |
| 3 | Выявление потребности | Настоящая мотивация: диплом, переезд, язык, карьера |
| 4 | Презентация под боль | Пакет предложен под ситуацию, а не зачитан прайс |
| 5 | Отработка «дорого» | Названа цена, отработана рассрочка / зачёт экспертной сессии |
| 6 | Гарантии и доверие | Договор, кейсы, что входит и чего нет |
| 7 | Следующий шаг с датой | Конкретный день и время, а не «я подумаю» |
| 8 | Тон и стоп-слова | Уважение, отсутствие давления и запрещённых обещаний |

На выходе модель обязана вернуть **строгую структуру** (structured outputs, `output_config.format` — схема валидируется на стороне API, парсить свободный текст не придётся):

```
итоговый_балл: 0–10
тип_клиента: горячий | тёплый | холодный | нецелевой
пункты[]: { код, балл 0–10, сильные_стороны[], зоны_роста[], цитата, таймкод }
следующий_шаг: { есть: bool, что, дата, цитата }
возражения[]: { какое, отработано: bool, как }
озвученные_суммы[]: числа
риски[]: например «обещана гарантия, которой нет в договоре»
краткое_резюме: 3–5 предложений для карточки
```

Каждая оценка обязана опираться на цитату с таймкодом. Оценка без цитаты не принимается — иначе разбор превращается в гадание, которое невозможно проверить.

### 4.5. Что разбор делает со сделкой

- `краткое_резюме` → запись в ленту активности (`activity_type = 'call'`).
- `следующий_шаг` → задача с дедлайном (`source = 'ai_next_step'`), назначена на продажника. Если шага нет — это **само по себе сигнал** и попадает в утреннюю панель РОПа.
- `тип_клиента` → подсказка по этапу («похоже на «Договор», перевести?»), но этап **не двигается автоматически**. Передвигает человек.
- `риски` → уведомление РОПу в Telegram сразу, не дожидаясь утра.
- Оценки → дашборд качества.

### 4.6. Модель и стоимость

**Модель разбора:** `claude-opus-5` (вход $5 / выход $25 за 1 млн токенов, окно 1 млн). Структурированный вывод поддерживается.

Расчёт на разговор 45 минут: расшифровка ≈ 12–18 тыс. токенов входа, ответ ≈ 1,5 тыс.
→ ориентировочно **$0,10–0,12 (≈ 9–11 ₽) за разбор**.

Расшифровка через Gemini — копейки на этом объёме.

При нашем потоке (≈ 50 консультаций в месяц по броням + дожимы) это **порядка 1 000–1 500 ₽ в месяц**. Деньги здесь не ограничение — поэтому предлагаю не экономить на качестве разбора.

Если захотите урезать вдвое — есть `claude-sonnet-5` ($3 / $15). Это ваше решение, не моё: на разборе диалога разница в качестве видна, а экономия в абсолюте меньше тысячи рублей в месяц. Ставлю Opus по умолчанию, модель задаётся настройкой `rop_settings.call_model` и меняется без выкатки.

Учёт расходов уже есть в схеме (`cost_accounting`, `model_pricing`) — подключаем к нему новую дорожку, чтобы стоимость разборов была видна в `/admin/finance`, а не выяснялась из счёта.

## 5. Блок 2 — Кабинет РОПа: контроль без прослушивания 100 % записей

### 5.1. Утренняя панель `/rop` (переделка главного экрана)

Ровно пять блоков, читается за 5 минут:

1. **Средняя оценка отдела** за 7 дней + динамика.
2. **Топ-3 проседающих пункта** чек-листа по отделу — это и есть тема планёрки.
3. **Продажники с аномально низкой долей «следующий шаг зафиксирован»** — главный операционный показатель.
4. **5–10 звонков «к прослушиванию сегодня»** — не случайных, а из корзин риска (см. 5.2).
5. **Что требует решения**: неотмеченные исходы консультаций, риски из разборов, неопознанные записи.

Всё остальное — во вкладки.

### 5.2. Корзины риска (умная выборка)

Вместо «слушать наугад» — правила, которые сами набирают список:

- звонок длиннее 4 минут без зафиксированного следующего шага;
- клиент назвал цену или сказал «дорого»;
- повторный контакт без движения этапа;
- первый звонок по новому лиду;
- звонки новичка в первые 30 дней;
- разговор с флагом «риск» от модели;
- оценка ниже порога (порог в `rop_settings`).

Каждая корзина — с нормой «сколько в неделю» и ответственным.

### 5.3. Качество по людям `/rop/quality`

- Рейтинг продажников по средней оценке (период настраивается).
- Разрез по пунктам чек-листа: у кого проседает квалификация, у кого — отработка цены.
- Динамика по неделям — видно, помогла ли планёрка.
- Распределение оценок (не только среднее — среднее скрывает, что половина звонков провальна).

### 5.4. Калибровка

Раз в месяц — режим калибровки: РОП оценивает 3 звонка вручную по тому же чек-листу, система показывает расхождение с моделью. Если расхождение системное — правится чек-лист или промпт. Без этого через три месяца никто не будет доверять оценкам, и правильно сделает.

### 5.5. Карточка разговора `/rop/calls/[id]`

Плеер + расшифровка с таймкодами и поиском + карточки по пунктам чек-листа + кнопка «к сделке». Клик по цитате в оценке — перемотка на этот момент записи. Это единственный способ проверить оценку за 10 секунд вместо 40 минут.

## 6. Блок 3 — Возврат из ожидания и допродажи

### 6.1. Очередь возврата `/sales/return` и `/rop/return`

Раз в сутки фоновая задача перебирает сделки в «Догрев», «На будущее», «Возражения» и старше N дней в активных этапах. Для каждой модель читает историю (лента + сообщения + разборы звонков) и возвращает:

- **вероятность возврата** (высокая / средняя / низкая) и почему;
- **повод** — конкретный, привязанный к тому, что человек говорил: «сомневался в бюджете → появилась рассрочка на 6 месяцев», «ждал результатов экзамена → они были в июне», «интересовалась Венгрией → дедлайн подачи 15 января»;
- **черновик первого сообщения** — в канал, где с ним уже общались (Telegram / WhatsApp);
- **чего делать не надо** — если человек прямо отказал, это видно и он в очередь не попадает.

Очередь отсортирована по вероятности. Продажник видит 10 карточек в день, не 136. Отправляет — человек, одной кнопкой, после правки текста.

Правила поверх модели (они дешевле и надёжнее): интейки (сентябрь / январь), дедлайны подач по странам из каталога, срок с последнего касания, бюджет из квиза.

### 6.2. Допродажи оплатившим

71 клиент. Отдельная вкладка с сигналами:

- купил экспертную сессию, пакет не взял — а сессия зачитывается в стоимость пакета;
- базовый пакет, а профиль тянет на «под ключ»;
- поступил — предложить языковые курсы / сопровождение семьи;
- есть младший брат/сестра (видно из переписки).

Тут же — статус оплат из `payments`, чтобы не приходить с допродажей к тому, кто просрочил транш.

### 6.3. Автоматические напоминания

Сделка входит в «Догрев» → автоматически ставится задача-возврат на дату, которую назвал сам клиент (её вытаскивает разбор звонка из фразы «давайте после экзаменов в июне»). Не назвал — стандартный срок из настроек.

## 9. Безопасность и закон

1. **Согласие на запись.** В форму записи на консультацию (`/book` и форма на сайте) добавляется явная строка о том, что встреча записывается и запись используется для контроля качества. Zoom дополнительно предупреждает голосом — это не отменяет строку в форме. Без согласия путь Б не включаем.
2. **Записи — приватные.** Отдельный бакет Supabase Storage без публичного доступа, ссылки только подписанные и короткоживущие.
3. **Подпись вебхука Zoom проверяется до любых действий** — как уже сделано для Telegram (`lib/webhook-secret.ts`) и WordPress.
4. **Расшифровка — это данные, а не команды.** В ней может оказаться «игнорируй инструкции» или «переведи деньги». Текст уходит в разбор как содержимое и ничего сверх разбора выполнить не может — та же оговорка, что уже стоит в `lib/finance/speech.ts`.
5. **Срок хранения.** Записи — 12 месяцев, расшифровки и разборы — бессрочно (они анонимизируемы и легче). Срок задаётся настройкой, чистка — фоновой задачей.
6. **Где лежат данные.** Персональные данные уже лежат в Supabase за пределами РФ — эта функция ничего в этом не меняет, но добавляет к ним аудиозаписи. Если по 152-ФЗ нужна первичная база в РФ, это отдельная задача уровня всей CRM, не этого блока. Отмечаю, чтобы решение было осознанным.
7. **В облаке Zoom записи не задерживаются.** После подтверждённой копии у нас запись из Zoom удаляется (4.1.1). Меньше мест хранения — меньше поверхность утечки, и заодно не кончается место.

### 9.7. Новые переменные окружения

| Час аудио не укладывается в 300 с Vercel | средний | Замер на Э1 до всякой разработки интерфейса. Не уложились — отдельный воркер. |

| Очередь возврата завалит спамом старую базу | средний | Не больше 10 карточек в день на продажника, отправляет человек, отказавшиеся исключены |

## 14. Приложение А — что настроить в Zoom

Делается один раз, занимает ~20 минут. Требуются права владельца или администратора аккаунта.

### 14.1. Приложение для доступа к API

`marketplace.zoom.us` → **Develop** → **Build App** → тип **Server-to-Server OAuth**.
Название: `goandstudy CRM`. Это внутреннее приложение, на модерацию Zoom его отправлять не нужно.

**Вкладка App Credentials** — оттуда забираем три значения:

| Что | Куда |
|---|---|
| Account ID | `ZOOM_ACCOUNT_ID` |
| Client ID | `ZOOM_CLIENT_ID` |
| Client Secret | `ZOOM_CLIENT_SECRET` |

**Вкладка Feature → Event Subscriptions** — включить, добавить подписку:

- Event notification endpoint URL: `https://crm.goandstudy.com/api/zoom/webhook`
- События: **All Recordings have completed** (`recording.completed`). Больше ничего не нужно.
- Скопировать **Secret Token** → `ZOOM_WEBHOOK_SECRET_TOKEN`

Кнопку «Validate» нажимаем **после** выкатки обработчика — до неё Zoom получит 404 и не даст сохранить.

**Вкладка Scopes** — семь областей доступа, ровно столько, сколько нужно:

| Зачем | Область | Раздел в списке |
|---|---|---|
| Создать встречу под бронь | `meeting:write:meeting:admin` | Meetings |
| Прочитать данные встречи | `meeting:read:meeting:admin` | Meetings |
| Перенос брони | `meeting:update:meeting:admin` | Meetings |
| Отмена брони | `meeting:delete:meeting:admin` | Meetings |
| Забрать файлы записи | `cloud_recording:read:list_recording_files:admin` | Recording |
| Удалить запись из облака после нашей копии | `cloud_recording:delete:meeting_recording:admin` | Recording |
| Сопоставить продажников с аккаунтами Zoom | `user:read:list_users:admin` | User |

Поиск в окне «Add Scopes» ищет и по идентификатору — вбивать строку из второй колонки быстрее, чем листать категории. Счётчик внизу должен показать **7 Selected**.

Названия областей в интерфейсе Zoom периодически меняются, идентификатор стабильнее: раскрыть строку шевроном справа и сверить по нему. «Select All» не использовать — там сотни областей, включая удаление пользователей и доступ к чатам.

В конце — **Activate your app**.

### 14.2. Настройки записи

**Admin → Account Management → Account Settings → вкладка Recording.**
Подписи даны так, как они стоят в интерфейсе Zoom.

**Cloud recording** — включить. Внутри блока:

| Пункт | Значение | Почему |
|---|---|---|
| `Record active speaker with shared screen` | выкл | Видео не нужно, а место ест в 10 раз больше |
| `Record gallery view with shared screen` | выкл | То же |
| `Record active speaker, gallery view and shared screen separately` | выкл | То же |
| `Record an audio only file` | **вкл** | Единственная дорожка, которая нам нужна |
| `Record a separate audio file of each participant who speaks` | **вкл** | Роли в расшифровке становятся точными |
| `Audio transcript` | вкл (необязательно) | Бесплатная расшифровка от Zoom как запасная. Свою мы всё равно делаем сами |
| `Allow cloud recording sharing` | **выкл** | Убирает публичные ссылки на записи — меньше поверхность утечки |

**Automatic recording** — включить, выбрать `Record in the cloud`.
Подпункт `Host can pause/stop the auto recording in the cloud` оставить **включённым**: если клиент против записи, у продажника должна быть возможность остановить её, а не выкручиваться.

**Recording disclaimer** — включить.

| Подпункт | Значение | Почему |
|---|---|---|
| `Ask participants for consent when a recording starts` | **вкл** | Участник видит и подтверждает — часть согласия по 152-ФЗ |
| `Ask host to confirm before starting a recording` | **выкл** | Иначе автозапись потребует нажатия от продажника, и смысл автоматики теряется |

После настройки — **залочить** каждый пункт значком замка справа, чтобы продажник не переключил у себя.

**Личный ID конференции (PMI) не используем.** У PMI один идентификатор на все встречи — по нему невозможно понять, чей это разговор. Каждая бронь получает свою встречу с уникальным id.

### 14.3. Лицензии и хост встречи — проверено 24.09.2026

**Аккаунтов Zoom два, оба с лицензией:**

| Почта | Имя в Zoom | Чей |
|---|---|---|
| `gs@goandstudy.com` | Goandstudy Образование за рубежом | **Общий рабочий — с него идут консультации продаж** |
| `gszoom@goandstudy.com` | GS Куратор | Кураторы |

Личных аккаунтов у продажников нет: все восемь заходят под общим `gs@`. Значит хостом встречи всегда будет этот аккаунт, а продажник — залогиненный под ним человек. Автозапись в облако при этом стартует штатно: хост в комнате есть.

**Одна лицензия на продажи = одна консультация одновременно.** Проверено по 181 слоту с 1 июня: два пересечения за четыре месяца (12 и 25 августа), трёх не было ни разу. То есть проблема редкая, но существует.

Правило при создании встречи:

1. Слот свободен у `gs@` — создаём под ним.
2. Занят — пробуем `gszoom@`, если на это время нет кураторской встречи.
3. Оба заняты — встречу не создаём, бронь остаётся, продажнику и РОПу падает уведомление «слот пересекается, назначьте другое время или заведите встречу вручную».

Занятость считаем по своим же броням, а не запросом в Zoom: мы знаем расписание раньше, чем Zoom. Кураторские встречи на `gszoom@` мы не видим — поэтому шаг 2 остаётся попыткой, а не гарантией.

Если пересечения станут частыми, дешёвое решение — третья лицензия под продажи (≈ 16 € в месяц), а не по лицензии на каждого: по замерам больше двух одновременных консультаций не бывает.

### 14.4. Вебхук приходит на весь аккаунт — записи кураторов надо отсекать

Подписка на события заводится на уровне аккаунта Zoom, а не отдельного пользователя. Значит `recording.completed` будет приходить **и на кураторские встречи с `gszoom@`**, и на любую другую запись в организации.

Без фильтра это означает: чужие разговоры расшифровываются, разбираются моделью по чек-листу продаж, попадают в «Неопознанные разговоры» и стоят денег.

Поэтому обработчик принимает запись только если выполнено одно из двух:

- `payload.object.id` совпадает с `bookings.zoom_meeting_id` — то есть встречу создали мы под конкретную бронь;
- либо хост — `gs@goandstudy.com` **и** на это время есть бронь консультации.

Всё остальное отбрасывается сразу, до скачивания файла, с записью в журнал. Список разрешённых хостов — в настройке `rop_settings.calls_zoom_hosts`, чтобы добавление третьей лицензии не требовало выкатки.

Это же правило защищает от неожиданного: кто-то записал внутреннюю планёрку — она не уедет в разбор продаж.

---|---|
| `gs@goandstudy.com` | Goandstudy Образование за рубежом |
| `gszoom@goandstudy.com` | GS Куратор |

Восемь продажников работают с этих двух общих аккаунтов, личных у них нет.

**Двух лицензий хватает.** Проверено по 181 слоту с 1 июня: одновременных консультаций было две всего в двух случаях (12 и 25 августа), трёх — ни разу. Покупать лицензии под каждого продажника не нужно.

Из этого следуют три решения:

1. **Хост выбирается программно, а не закрепляется за продажником.** При создании встречи берём свободный на это время аккаунт: основной — тот, что отведён под продажи, второй — запасной для редкого пересечения. Занятость считаем по нашим же броням, а не запросом в Zoom: мы знаем расписание раньше, чем Zoom.
2. **Сшивка по хосту бесполезна.** Уровень 3 из раздела 15 (совпадение по хосту и времени) на общих аккаунтах ничего не даёт — хост один и тот же у всех. Остаётся уровень 1 (`meeting_id`), который и так покрывает всё, и ручная привязка для редких исключений. Уровень 3 применяем только как «бронь этого времени», без проверки хоста.
3. **Место в облаке считается на аккаунт целиком**, а не на продажника. Ещё один довод за звук вместо видео и за очистку после переноса в наш Storage (14.1.1).

## 15. Приложение Б — как определяется, чей это разговор

Четыре уровня, сверху вниз. Ожидаю, что 95 % попадёт на первом.

### Уровень 1 — точное совпадение по встрече (основной)

При создании брони мы сами создаём встречу в Zoom:

```
POST /users/{host}/meetings
  topic:      "Консультация · Иван Петров · сделка 1f2e…"
  start_time: время слота
  duration:   30
  settings:   { auto_recording: "cloud" }
→ meeting_id, join_url
```

`meeting_id` и `join_url` сохраняются в бронь. Когда приходит вебхук:

```
payload.object.id  →  bookings.zoom_meeting_id  →  booking.id  →  deals.booking_id  →  сделка
```

Совпадение однозначное. Угадывать не нужно.

Побочные выгоды, которых сейчас нет:

- ссылка на встречу появляется в Telegram-уведомлении продажнику сразу;
- её можно автоматически отправить клиенту в Telegram, если он оставил `@username` (поле `client_telegram` в брони уже заполняется);
- запись включается сама — `auto_recording: "cloud"` задаётся прямо при создании встречи, независимо от того, что настроено у продажника.

**Перенос брони** — обновляем ту же встречу (`PATCH /meetings/{id}`), идентификатор не меняется, связь не рвётся.
**Отмена** — удаляем встречу, чтобы по мёртвой ссылке никто не зашёл.

### Уровень 2 — тема встречи

В `topic` зашиты имя клиента и идентификатор сделки. Это страховка для человека: если что-то пойдёт не так, в списке записей Zoom видно глазами, к кому относится файл. Автоматика на тему не опирается — её может переписать продажник.

### Уровень 3 — хост и время

Продажник провёл встречу мимо брони (запустил свою конференцию). Тогда ищем бронь **этого же продажника** в окне ±90 минут от начала записи. Одна нашлась — привязываем и помечаем «связано по времени, проверьте». Несколько — не угадываем, уходим на уровень 4.

Дополнительная зацепка: почта и телефон участников из `payload.object.participant_*`, если человек заходил авторизованным — сверяем с `deals.phone_normalized` и `contact_email`.

### Уровень 4 — «Неопознанные разговоры»

Не сошлось ничего — запись всё равно расшифровывается и разбирается, но лежит в отдельном списке на `/rop/calls` с пометкой. Привязка к сделке — один клик с поиском по имени и телефону. Пустых записей в системе не остаётся: то, что не привязалось, видно, а не потеряно.

### Ручная загрузка

Файл грузится **внутри карточки сделки** — вопрос принадлежности не возникает по построению.
