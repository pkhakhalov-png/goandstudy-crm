# Разведка: Telegram

_17 сентября 2026. Решение: **CONDITIONAL** — упирается в токен бота от Павла._

Разведка отвечает на шесть вопросов до того, как написана первая строка
коннектора. Смысл в том, чтобы выяснить «не получится» дёшево, а не в середине
реализации.

## 1. Документация

[core.telegram.org/bots/api](https://core.telegram.org/bots/api) — **Bot API
10.3, 24 августа 2026**. Дата важна: документация без даты не позволяет
отличить «так устроено» от «так было устроено».

Публикация в канал делается `sendMessage` (обязательные поля `chat_id` и
`text`) и `sendPhoto` для поста с картинкой. Превью ссылки управляется
`link_preview_options`; старое поле `disable_web_page_preview` заменено, и код,
написанный по памяти образца двухлетней давности, встретится с этим не сразу.

## 2. Доступность

Измерено, а не предположено. С машины разработки:

```
api.telegram.org/bot0:0/getMe → HTTP 401 за 0,377 с
{"ok":false,"error_code":401,"description":"Unauthorized: invalid token specified"}
```

Ответ «неверный токен» здесь — **успех проверки**: сеть есть, TLS сошёлся,
сервис отвечает по существу.

Но эта машина в Москве и, возможно, за VPN, а публиковать будет сервер. Это
разные сети и, вполне возможно, разные ответы. Поэтому заведён эндпоинт
`GET /api/content/reach` — он делает ту же проверку **оттуда, где выполняется
наш код**, и заодно показывает площадку и регион. Открыть после выкладки,
залогинившись админом.

Отдельно: телеграм-публикации **не требуют** VPS в Амстердаме, о котором идёт
речь в ADR-0001. Тот нужен модельным API. Отправку поста может делать та же
Vercel, на которой стоит CRM, — если проверка достижимости оттуда пройдёт.

## 3. Квоты

Из [FAQ](https://core.telegram.org/bots/faq):

| Ограничение | Значение |
|---|---|
| В один чат | не чаще одного сообщения в секунду |
| В группе | не больше 20 сообщений в минуту |
| Массовая рассылка | около 30 сообщений в секунду |
| При превышении | HTTP 429 |

**Наш темп — один пост в день.** До квот три порядка запаса, и ограничение
скорости не является риском этого проекта. Писать сложное управление темпом под
телеграм не нужно; хватит того, что уже есть в планировщике.

Риск в другом месте, см. пункт 6.

## 4. Права

Бот должен быть **администратором канала с правом `post_messages`**
([ChatAdminRights](https://core.telegram.org/constructor/chatAdminRights)).
Обычного членства недостаточно.

`chat_id` принимает две формы: числовой идентификатор канала (с приставкой
`-100`) и `@имя_канала`. Хранить нужно **числовой**: имя канала может быть
изменено владельцем, и тогда публикация уйдёт не туда или не уйдёт вовсе.

## 5. Тестовый remote ID — не получен

Это единственный пункт разведки, который не закрыт, и закрыть его без Павла
нельзя: нужен токен бота и канал, где бот сделан администратором.

Разведка без тестовой публикации отвечает на вопрос «должно работать», а не
«работает». Разница между ними — это и есть то, ради чего разведку проводят,
поэтому решение ниже условное, а не положительное.

**Что нужно от Павла:** токен бота (`BOT_TOKEN` от @BotFather) и канал, где
этот бот администратор с правом публикации. Тестовый канал подойдёт — боевой
для этого не нужен.

## 6. Настоящий риск: неизвестный исход

Главное, что выяснила разведка, — не квоты.

**Bot API не поддерживает ключ идемпотентности.** У `sendMessage` нет поля, по
которому повтор был бы распознан как повтор. И **бот не может прочитать историю
чата**: `getUpdates` и вебхуки отдают только новые события, метода «покажи
последние сообщения канала» не существует.

Отсюда следует неприятное. Если запрос на отправку ушёл, а ответ не дошёл —
сеть моргнула, функция упёрлась в таймаут, — узнать, опубликовалось сообщение
или нет, **штатными средствами нельзя**. Слепой повтор в этой ситуации даёт
второй пост в канале.

Это ровно то состояние, которое PRD называет `unknown_outcome`, и для телеграма
оно не теоретическое, а основное.

Что с этим можно сделать (проверять тестовой публикацией):

1. **Метка в тексте.** В пост встраивается невидимый или незаметный
   идентификатор публикации. При неизвестном исходе следующий шаг ищет метку.
   Ищет — где? См. пункт 2 ниже.
2. **Обновления `channel_post`.** В объекте Update есть `channel_post` —
   «новый входящий пост канала». Приходят ли туда посты, сделанные самим
   ботом, документация не говорит. Если приходят — это и есть способ узнать
   исход; если нет — способа нет. **Проверяется тестовой публикацией**, и это
   вторая причина, по которой без токена разведка не закрыта.
3. **Разбор человеком.** Если первые два не работают, `unknown_outcome`
   становится вопросом в очередь внимания: «отправляли, исход неизвестен,
   посмотри в канале». Честно, дёшево и не создаёт дублей — но требует
   человека.

Худший вариант — третий, и он приемлем: при темпе один пост в день неизвестный
исход будет случаться редко, а два поста подряд в канале читатель заметит
раньше нас.

## Решение: CONDITIONAL

**За.** Документация свежая и полная, API простой, сеть доступна, квоты на три
порядка выше нашего темпа, права понятны.

**Против.** Нет ключа идемпотентности и нет чтения истории, поэтому
`unknown_outcome` не разбирается автоматически — во всяком случае, пока не
проверено поведение `channel_post`.

**Условие снятия:** токен бота и тестовая публикация в реальный канал, по
которой выясняется (а) реальный remote ID и формат ссылки на пост, (б)
приходит ли собственный пост в `channel_post`. После этого решение
перечитывается и становится GO или превращается в план обхода.

**Чего делать не надо:** писать коннектор в расчёте на то, что
`unknown_outcome` разберётся сам. Пока не проверено — не разберётся.
