# Архитектура кабинета куратора v2

**Статус:** проект архитектуры. Код не написан, миграции не применялись, боевая база не менялась.
**Основание:** `docs/AUDIT_CURATOR_AI.md`, чтение кода 25.09.2026, `docs/DESIGN_CURATOR_V2.md`.
**Главное ограничение:** действующий кабинет куратора продолжает работать без единого изменения поведения.

---

## 0. Как обеспечивается «ничего не сломать»

Не обещанием, а свойствами конструкции. Четыре уровня, каждый проверяем.

**Уровень 1. Ни одного изменения существующих таблиц.** Всё новое живёт в отдельной схеме `care`. Ни одной `ALTER TABLE` по `public.*`. Если завтра схему `care` удалить целиком (`drop schema care cascade`), действующая CRM не заметит.

**Уровень 2. Ни одного изменения существующих файлов, кроме одной строки.** Новый код — новые каталоги `app/care/*`, `lib/care/*`, `app/api/care/*`. Единственная правка общего файла — одна строка в `middleware.ts` (раздел 3.3), и та добавляет маршрут в список исключений через `||`, не трогая условия существующих.

**Уровень 3. У кода нового кабинета нет прав на запись в рабочие таблицы.** База одна и боевая — по решению владельца. Поэтому защита перенесена в саму базу: новый кабинет ходит под ролью `care_app`, которой выдано право писать только в `care` и читать перечисленные таблицы `public`. Попытка записи в `public.clients` заканчивается отказом базы, а не надеждой на внимательность (раздел 2.1).

**Уровень 4. Разные исполнители.** Новая очередь — свои задания, свой воркер, свой секрет, своё расписание. В `seo.jobs` не добавляется ни одной задачи. Падение нового кабинета не может остановить производство статей, и наоборот.

Проверки этих четырёх свойств — часть приёмки (раздел 11). Отдельно: боевые ключи внешних сервисов используются, но наружу ничего не уходит — три независимых условия должны совпасть, чтобы отправка состоялась (раздел 2.6).

## 2. Изоляция при работе в боевой базе

**Решение владельца от 25.09.2026:** отдельный проект Supabase не заводится. Новый кабинет живёт в **той же базе** (`pxtwaxhmygnssyyowrgr`), в отдельной схеме `care`. Внешние сервисы — боевыми ключами, внешние отправки выключены.

Это снимает пункт «рабочая среда не содержит ключей на запись в production» из первоначального плана. Взамен ставится защита, которая сильнее дисциплины в коде: **новый кабинет получает собственную роль Postgres, физически лишённую права записи в `public`.**

### 2.1. Роль `care_app` — главная защита

PostgREST переключается на роль из claim `role` в JWT. Значит можно выдать новому кабинету ключ, у которого прав меньше, чем у service-role.

```
create role care_app nologin;
grant care_app to authenticator;              -- иначе PostgREST не переключится

grant usage on schema care to care_app;
grant select, insert, update, delete on all tables in schema care to care_app;
grant usage on all sequences in schema care to care_app;

grant usage on schema public to care_app;
grant select on public.clients, public.curators, public.users,
                 public.client_applications, public.client_universities,
                 public.client_documents, public.client_tg_messages,
                 public.curator_stages, public.curator_stage_checklist,
                 public.deals
      to care_app;                            -- ТОЛЬКО select, перечислением
```

Что это даёт:

| Попытка | Результат |
|---|---|
| `insert/update/delete` в любую таблицу `public` | отказ на уровне базы: `permission denied` |
| `alter`, `drop`, `create` где угодно | отказ: у роли нет DDL |
| чтение таблиц `public`, не входящих в список (`payments`, `expenses`, `deal_analyses`) | отказ |
| работа с `care.*` | разрешено |
| обход через RLS | невозможен: `care_app` не `BYPASSRLS` |

Ошибка в коде нового кабинета не может испортить данные кураторов — не потому что код аккуратный, а потому что ключу не выданы права. Это проверяемо (раздел 11) и снимается только отдельной миграцией.

**Ключ.** `CARE_DB_KEY` — JWT, подписанный секретом проекта, payload `{ role: 'care_app', iss: 'supabase' }`. Кладётся в `.env.local` и в переменные Vercel. Ключ `SUPABASE_SERVICE_ROLE_KEY` в коде нового кабинета **не читается ни разу** — запрещено правилом ESLint и проверяется приёмкой.

### 2.2. Что всё-таки остаётся на service-role

Три операции, которым мало прав `care_app`:

1. **Миграции** — применяются как сейчас, через Management API (`scripts/apply-sql.ts`), вручную, по одному файлу.
2. **Чтение профиля пользователя при входе** — уже делает существующий код кабинета, новый его переиспользует на чтение.
3. **Перенос данных** (раздел 10) — читает `public`, пишет в `care`; запускается вручную, не из приложения.

Первое и третье — скрипты, запускаемые человеком, не приложением. В коде приложения service-role-клиента нет.

### 2.3. Предохранитель миграций

`scripts/care/check-sql.ts` — запускается перед каждым применением и отказывает, если в файле есть:

- любое `alter table public.` / `drop` / `truncate` / `delete from public.`;
- `create table` вне схемы `care`;
- упоминание `seo.jobs`, `public.clients` в позиции записи;
- отсутствие парного файла `*.rollback.sql`.

Проверка встроена в `scripts/apply-sql.ts`: файл из каталога `supabase/migrations/care/` без прохождения проверки не применяется.

Это заменяет прежний «предохранитель адреса базы»: адрес теперь боевой намеренно, защищать нужно не от базы, а от содержания миграции.

### 2.4. Отпечаток и режим

`care.env_marker` — одна строка: `mode = 'pilot' | 'prod'`, `external_sends = false`, `updated_by`, `updated_at`. Приложение читает её при старте. Пока `external_sends = false`, модуль отправок наружу ничего не отправляет, что бы ни говорили переменные окружения. Изменить можно только миграцией, не из интерфейса.

Смысл: рубильник живёт в базе, а не в переменной окружения Vercel, где его легко переставить случайным деплоем.

### 2.5. Внешние сервисы боевыми ключами

| Сервис | Как используется | Чем ограничено |
|---|---|---|
| Anthropic | боевой `ANTHROPIC_API_KEY` | свой учёт расходов `care.cost_ledger`, дневной потолок, резерв до вызова. Расход виден отдельно от SEO |
| Zoom | боевое приложение | только **чтение** записей и расшифровок. Встречи новый кабинет не создаёт и не удаляет |
| Telegram | боевой бот | отправка только через `lib/care/outbound.ts`, который при `external_sends = false` пишет в `care.outbox` со статусом `suppressed` и наружу не ходит |
| Wazzup | боевой ключ | то же; на первом этапе не используется вовсе |
| Каталоги вузов и стипендий | боевые проекты | anon-ключи, только чтение. Service-role-ключи каталогов в новом коде не читаются |

### 2.6. Рубильник внешних отправок

Единственная дверь наружу — `lib/care/outbound.ts`. Прямые импорты `lib/telegram.ts`, `lib/wazzup.ts`, `lib/zoom/client.ts` из `lib/care/*` и `app/care/*` запрещены правилом ESLint `no-restricted-imports` — сборка падает.

Три условия должны совпасть, чтобы сообщение ушло наружу:

1. `care.env_marker.external_sends = true` (только миграцией);
2. флаг `outbound` включён для этого клиента или куратора;
3. предложение типа «сообщение» подтверждено куратором, и его `content_hash` совпадает с подтверждённым.

Любое из трёх не выполнено — строка в `care.outbox` со статусом `suppressed` и честный ответ «подавлено», а не «успешно».

### 2.7. Тестовые данные в боевой базе

Раз база одна, синтетические клиенты окажутся рядом с настоящими. Правила:

- синтетика живёт **только** в `care.*` (`care.cases` с `is_synthetic = true`), в `public.clients` не создаётся ни одной строки;
- новый кабинет умеет показывать синтетические дела, старый их не видит вовсе — он про схему `care` не знает;
- файлы тестовых загрузок — в отдельный бакет `care-files`, боевые бакеты не трогаются;
- очистка синтетики — одна команда `delete from care.cases where is_synthetic`.

### 2.8. Что изменится в боевом проекте и когда

| Изменение | Когда | Обратимость | Влияние на работу кураторов |
|---|---|---|---|
| `create schema care` + таблицы + роль | на этапе 2 | `drop schema care cascade`, `drop role care_app` | нет: существующий код о схеме не знает |
| Добавление `care` в Exposed schemas | перед первым обращением приложения | вернуть прежнюю строку | **перезапуск PostgREST на несколько секунд** — делать в согласованное время |
| Переменные `CARE_*` на Vercel | при первом деплое ветки | удалить | нет |
| Бакет `care-files` | этап 2 | удалить | нет |
| Задача `pg_cron` для `/api/care/tick` | этап 4 | `cron.unschedule` | нет: отдельная задача, существующие не трогаются |

Единственный пункт с видимым влиянием — второй. Прошу назначить удобное время; операция занимает секунды, но приходится на живой API.

## 3. Размещение кода

### 3.1. Ветка и рабочая копия

Ветка `feat/curator-v2` от `main`, связь с основным репозиторием сохраняется. Слияние в `main` — отдельное решение владельца после приёмки. Пока ветка не слита, боевой Vercel (деплой с `main`) физически не может собрать новый код.

Правило: **из `lib/care/*` и `app/care/*` нельзя импортировать модули, делающие запись** в существующие контуры. Разрешены импорты на чтение (`lib/supabase/read-all.ts`, типы, форматирование). Запрет фиксируется правилом ESLint `no-restricted-imports` с явным списком.

### 3.3. Единственная правка общего кода

`middleware.ts`, список публичных маршрутов, одна строка:

```diff
     pathname.startsWith('/api/seo') ||     // воркер SEO: своя авторизация по x-seo-tick-secret
+    pathname.startsWith('/api/care') ||    // воркер и вебхуки нового кабинета: свой секрет
     pathname.startsWith('/api/track')
```

Зачем: воркер зовут по расписанию без сессии, иначе middleware отправит его на `/login`. Авторизация — заголовок `x-care-tick-secret`, проверяется внутри маршрута, как у SEO.

Почему это безопасно: добавление ветки в цепочку `||` не меняет результат ни для одного существующего пути. Маршрутов `/api/care/*` в боевом коде нет — до слияния строка не делает ничего вообще.

Кабинет `/care` в middleware **не упоминается**: анонима отсекает общее правило, а роль проверяет `app/care/layout.tsx`. Ноль правок ради интерфейса.

## 4. Применимость предпочтительного варианта переключения

Плана пункт 8: после одобрения применить к рабочей базе совместимые добавочные изменения и включать новую версию флагами. **Вариант применим.** Обоснование по коду:

1. **Новых колонок в существующих таблицах не требуется.** Связь с клиентом — внешним ключом из `care.*` в `public.clients(id)`. Ни одной `ALTER TABLE public.*` в миграциях нового кабинета нет и не планируется.
2. **Существующий код не увидит новых таблиц.** Он обращается к таблицам по именам; чужая схема в его запросы не попадает.
3. **Триггеров на существующие таблицы не навешиваем.** Синхронизация делается в коде нового кабинета (раздел 6.6), а не триггером — триггер на `public.clients` был бы вмешательством в работу действующей CRM.
4. **Ключи совместимы.** `clients.id` — integer, `curators.id` и `users.id` — uuid; внешние ключи новых таблиц ссылаются на них напрямую, без переносов идентификаторов.
5. **Флаги — отдельная таблица `care.feature_flags`.** Пустая таблица означает «новый кабинет выключен для всех». Это состояние по умолчанию после применения миграций.

**Что всё-таки является изменением настроек боевого проекта** (не миграцией) и требует отдельного согласия в момент переключения:

- включение схемы `care` в Exposed schemas настроек API Supabase — одна настройка, обратимая, данные не трогает;
- добавление расписания `pg_cron` для воркера `/api/care/tick` — отдельная задача расписания, не изменяющая существующие;
- новые переменные окружения `CARE_*` на боевом Vercel;
- новые бакеты хранилища.

Каждый пункт — в инструкции переключения отдельной строкой с проверкой и откатом. Если владелец не хочет менять настройки API, есть запасной вариант: положить те же таблицы в `public` с префиксом `care_`. Тогда настройки проекта не трогаются вовсе, но теряется возможность удалить всё одной командой. Решение — за владельцем, на архитектуру не влияет.

## 5. Слои

```
  интерфейс          app/care/*            экраны, ничего не решают
      │
  операции           lib/care/*/operations  разрешённые действия: одна функция = одно действие
      │   ▲                                 вызывается и кнопкой, и инструментом ИИ
      │   └──────────── инструменты ИИ      lib/care/tools/*  обёртка + проверка + журнал
      │
  данные             care.*                 факты, предложения, задачи, журнал
      │
  исполнение         care.jobs + /api/care/tick
```

Ключевое правило: **модель не имеет отдельного пути к данным.** Кнопка в интерфейсе и инструмент ИИ вызывают одну и ту же функцию-операцию с одинаковой проверкой прав. Произвольного SQL у модели нет, service-role-клиент ей не передаётся, набор инструментов — закрытый список.

### 5.1. Контракт операции

```
operation(actor, input) → { ok, changes[], error? }

actor   = { userId, curatorId, role, onBehalfOf: 'human' | 'ai', dialogId? }
input   = разобранный и проверенный объект (схема Zod), не сырой FormData
changes = что именно изменилось: таблица, идентификатор, поле, было, стало
```

Каждая операция обязана: проверить роль, проверить принадлежность клиента, проверить разрешение автономности для этого типа действия, записать в `care.audit`, вернуть перечень изменений (для истории и для отмены).

### 5.2. Контракт инструмента ИИ

Инструмент — тонкая обёртка над операцией:

```
tool = {
  name,                 // care.profile.apply, care.shortlist.propose, …
  schema,               // строгая схема аргументов
  mode,                 // 'read' | 'propose' | 'act'
  operation,            // что вызвать
}
```

- `read` — только чтение контекста, ничего не меняет.
- `propose` — создаёт запись в `care.proposals`, данные клиента не трогает.
- `act` — меняет данные; вызывается напрямую **только** если политика автономности для этого типа = «авто», иначе принудительно понижается до `propose`.

Понижение делает слой инструментов, а не модель. Модель не может «решить» действовать самостоятельно: её вызов `act` при политике «подтвердить» превращается в предложение, и она получает ответ «подготовлено, ждёт подтверждения».

## 6. Данные

Схема `care`. Все таблицы с `enable row level security` и **без разрешающих политик** — доступ только service-role из кода. Это строже, чем в `public`, и не даёт анон-ключу прочитать данные клиентов, даже если схему откроют для API.

### 6.1. Опора на существующие сущности

| Что | Решение |
|---|---|
| `public.clients` | **остаётся единственной карточкой клиента.** Второй карточки не создаём |
| `public.curators`, `public.users` | остаются, новые таблицы ссылаются на них |
| `public.client_applications`, `client_universities`, `client_documents`, `client_tg_messages` | **остаются рабочими**; новый кабинет читает их и постепенно дополняет своими сведениями, не дублируя записи |
| `public.curator_stages` (12 этапов, 64 пункта) | справочник переиспользуется как есть |
| `clients.project_data`, `roadmap_data` (jsonb) | читаются как источник; новые факты пишутся в `care.facts` с указанием происхождения. Обратная запись в jsonb — только при переключении (раздел 10) |

### 6.2. Таблицы

**Дело и цикл**

- `care.cases` — дело клиента: `client_id → public.clients(id)`, `cycle_year`, `status` (`active|paused|done|declined`), `opened_at`, `closed_at`. Один клиент — одно активное дело на цикл. Это и есть недостающий цикл поступления: повторное обращение через год — новая строка, старая не мешает.
- `care.case_members` — участники дела: куратор, второй куратор, профориентолог. Роль и период. Решает нехватку «одного ответственного», не трогая `clients.curator_id` (он остаётся источником правды для действующего кабинета).

**Факты и происхождение**

- `care.facts` — единица знания о клиенте: `case_id`, `key` (`budget_year`, `language_level`, …), `value` (jsonb), `unit`, `status` (`proposed|confirmed|rejected|stale`), `confidence`, `valid_from`, `checked_at`.
- `care.fact_sources` — откуда: `fact_id`, `source_kind` (`transcript|document|message|quiz|manual|web`), `source_id`, `quote`, `location` (тайм-код или страница), `captured_at`.
- `care.fact_history` — что было раньше: прежнее значение, кто и когда изменил, по какому предложению.
- `care.conflicts` — противоречие: два факта одного ключа из разных источников, статус разрешения.

Правило: факт без хотя бы одного источника не может получить статус `confirmed`. Факт из машинного разбора без цитаты не попадает в пакетное подтверждение.

**Материалы**

- `care.meetings` — встреча: тип, дата, ссылка на `public.bookings`/`call_recordings`, если есть.
- `care.transcripts` — расшифровка: `meeting_id` или ручная загрузка, текст, язык, длительность, хеш файла (защита от повторной загрузки того же).
- `care.documents` — документ дела: тип, статус, `storage_path`, `version`, `supersedes_id`, хеш. **Версии не удаляются** — в отличие от `finalizeDocumentUpload`, который затирает прежний файл.
- `care.doc_requirements` — требование к документу: откуда взялось (вуз, программа, страна), формулировка, источник и дата проверки.

**Работа**

- `care.shortlists` и `care.shortlist_items` — подборка с версиями: `version`, `status` (`draft|sent|approved`), `approved_by`, `approved_at`. Элемент несёт `school_id`/`program_id` из каталога, требования с датой проверки и пометку «сведения не найдены».
- `care.tasks` — задача: `case_id`, `title`, `assignee_kind` (`curator|client|specialist|ai`), `due_at`, `status`, `blocked_by` (массив задач), `waiting_on` (`client|curator|university|none`) — то самое «от кого ждём», которого нет сейчас нигде.
- `care.plans` / `care.plan_versions` — план как версионируемый документ, из которого раскрываются задачи.

**ИИ**

- `care.dialogs`, `care.messages` — диалог по клиенту: роль, текст, стоимость, использованные инструменты.
- `care.proposals` — предложение: `case_id`, `kind`, `payload` (что применить), `basis` (снимок входных данных), `content_hash`, `status` (`draft|ready|applied|rejected|stale|failed`), `created_by` (`ai|rule`), `decided_by`, `decided_at`.
- `care.proposal_items` — построчный дифф: поле, было, стало, источник, цитата. Нужен для частичного применения («Выбрать» в дизайне).
- `care.audit` — журнал: предложено / подтверждено / выполнено / ошибка, актёр (человек или ИИ), инструмент, вход, выход, стоимость, длительность.

**Исполнение**

- `care.jobs` — очередь, копия механики `seo.jobs` (раздел 7).
- `care.outbox` — исходящие наружу: канал, получатель, содержание, `idempotency_key`, статус (`queued|sent|suppressed|failed|unknown`).
- `care.cost_ledger`, `care.budget` — расход по дням и дело, потолок.
- `care.feature_flags` — включение по клиенту, куратору, всем (раздел 9).
- `care.env_marker` — отпечаток среды (раздел 2.3).

### 6.3. Почему факты отдельной таблицей, а не колонками

Колонки не несут происхождения. Аудит (блок В.2) называет это главным пробелом: вывод модели не отличить от проверенного факта. Таблица фактов даёт источник, цитату, дату проверки, историю и конфликт — то есть ровно то, что дизайн показывает шестью состояниями поля. Колонками это пришлось бы дублировать трижды.

Цена: чтение профиля — не `select *`, а сборка. Она делается один раз в `lib/care/context` и кешируется на запрос (образец — `lib/auth/viewer.ts` с `cache`).

### 6.4. Дубли: что где остаётся

| Сведение | Источник правды сейчас | В новом кабинете | Правило |
|---|---|---|---|
| Имя, телефон, почта, куратор | `public.clients` | там же | новый кабинет **не пишет** в эти поля в режиме параллельной работы |
| Профиль студента | `clients.project_data` | `care.facts` | читаем jsonb как источник `quiz/manual`; пишем в факты; обратная синхронизация — только по флагу (6.6) |
| Подборка | `client_universities` | `care.shortlist_items` | пока клиент не переведён — новый кабинет читает старую таблицу и показывает её как версию 0 |
| Заявки | `client_applications` | остаются там же | новый кабинет читает и пишет через операции, дублирующей таблицы нет |
| Документы | `client_documents` | `care.documents` | новые загрузки — в новую таблицу с версиями; старые видны только на чтение |
| Этап | `clients.current_stage_code` | он же | этап остаётся единым для обоих кабинетов, чтобы не разъехалось |

### 6.5. Один клиент — одна карточка

Второй независимой карточки не создаётся. `care.cases` — надстройка над `public.clients`, а не его копия. Отображение один к одному: `cases.client_id` уникален в пределах `cycle_year`.

### 6.6. Синхронизация к старому кабинету

Чтобы куратор, работающий в старом интерфейсе, видел результат работы нового (важно для пилота и для возврата), подтверждённые факты **опционально** записываются обратно в `clients.project_data`:

- только факты со статусом `confirmed`;
- только по флагу `sync_to_legacy` для конкретного клиента;
- запись идёт через операцию с журналом, а не триггером;
- при выключении флага синхронизация останавливается, ранее записанное остаётся.

По умолчанию флаг **выключен**. Включается поклиентно на пилоте — и только он даёт новому кабинету писать в `public.clients`, чего роль `care_app` не умеет. Поэтому обратная синхронизация выполняется не приложением, а отдельным скриптом под service-role, запускаемым человеком.

## 7. Очередь и фоновые операции

### 7.1. Почему своя очередь

План прямо запрещает подмешивать задания в SEO-очередь. Кроме того: у `seo.claim_jobs()` лимиты конкуренции заданы по дорожкам в `seo.settings`, и чужая нагрузка сместила бы производство статей. Поэтому `care.jobs` — **копия механики, но отдельная таблица, отдельная функция выдачи, отдельный воркер и отдельное расписание**.

Копируется (включая уже сделанные исправления):
- аренда с `FOR UPDATE SKIP LOCKED` и проверкой статуса во второй фазе (исправление двойной выдачи, `20260917000000`);
- fencing-token: воскресший исполнитель не запишет результат;
- `dedup_key UNIQUE` — повторное событие не создаёт вторую задачу;
- `attempts` / `max_attempts` / `next_run_at` с отступом;
- учёт стоимости и резервирование бюджета до вызова модели.

### 7.2. Воркер

`/api/care/tick`, `maxDuration = 300`, бюджет 240 с, батч меньше (2–3): шаги ИИ дороже и дольше SEO-шагов. Правило «не начинать длинный шаг под конец бюджета» переносится дословно — иначе Vercel убьёт функцию посреди вызова модели.

Авторизация — `x-care-tick-secret`, свой секрет, не `SEO_TICK_SECRET`. Расписание — отдельная задача `pg_cron` в том же проекте; существующие задачи не изменяются.

### 7.3. Шаги первого сценария

```
transcript_ingest    → сохранить расшифровку, посчитать хеш, отсечь повтор
transcript_extract   → факты и договорённости со строгой схемой и цитатами
facts_diff           → сопоставить с текущими фактами, найти конфликты
proposal_build       → собрать care.proposals + proposal_items
shortlist_research   → требования вузов, даты проверки, пометки «не найдено»
plan_build           → план и задачи со сроками и зависимостями
docs_instruction     → инструкция по документам с источниками требований
outbound_send        → отправка через outbox (в тесте — подавление)
```

Каждый шаг — отдельное задание. Прогресс между шагами живёт в базе, потому что памяти между вызовами функции нет.

### 7.4. Надёжность (пункт 6 плана)

| Требование | Как выполнено |
|---|---|
| Повтор без дублирования результата | `dedup_key` на задании + `content_hash` предложения: повторный разбор той же расшифровки не создаёт второе предложение |
| Защита от повторной отправки | `care.outbox.idempotency_key` уникален; отправка — две фазы: пометить `sending` → отправить → пометить `sent` |
| Актуальность перед применением | у предложения хранится `basis` — снимок входных фактов и их версий; перед применением сверяется. Разошлось → статус `stale`, применение запрещено |
| Подтверждение к версии | подтверждается `content_hash`; изменилось содержание — прежнее подтверждение недействительно (раздел 6.3 дизайна) |
| Повторная проверка прав в фоне | воркер перед выполнением заново зовёт проверку «этот куратор всё ещё ведёт этого клиента». Передали клиента — задание отменяется, а не выполняется от имени прежнего куратора |
| Отмена невыполненного | `status = cancelled` у задания и предложения; выполняющийся шаг доводится, следующие не запускаются |
| Ошибка ≠ неизвестный исход | у отправки отдельный статус `unknown`: ответ не получен, повтор запрещён, требуется ручная проверка |
| Ограничение стоимости и попыток | резерв бюджета до вызова, `max_attempts`, дневной потолок на куратора и на дело |

## 8. ИИ: контекст, инструменты, безопасность

### 8.1. Единый контекст

`lib/care/context/build.ts` — по образцу `lib/sales/conversation-source.ts`. Собирает снимок: клиент, дело, цикл, факты с происхождением, подборка, заявки, документы, задачи, последние сообщения, прошлые встречи. Каждый элемент несёт пометку происхождения и дату.

Снимок **типизирован и ограничен по объёму**: в модель уходит не «всё, что нашли», а отобранное под задачу, с явным списком того, что пропущено. Куратор может посмотреть, что именно было прочитано (в дизайне — кликабельные строки хода работы).

### 8.2. Разделение данных и команд

Аудит (блок 13) отмечает: сейчас защита от инъекций — оговорка в тексте промпта. Этого мало, когда появляются инструменты. Конструкция:

1. Содержимое расшифровок, документов и сообщений передаётся **отдельным блоком с пометкой «данные»** и никогда не смешивается с инструкцией оператора.
2. Инструменты `act` недоступны на шагах, которые читают внешний текст (`transcript_extract`, разбор документа). Эти шаги умеют только возвращать структуру — менять данные им нечем.
3. Любое изменение проходит через предложение, у которого есть источник и цитата. Инъекция «перевести деньги» не имеет цитаты из легитимного источника и упирается в подтверждение куратора.
4. Внешние отправки не могут быть инициированы содержимым документа: канал и получатель берутся из дела, а не из текста.

### 8.3. Стоимость и модели

Свой ключ, свой потолок, запись в `care.cost_ledger` при каждом вызове, резерв до вызова. Модели — актуальные (`claude-opus-5` для разбора, `claude-sonnet-5` для рутины). Устаревший `claude-sonnet-4-6` в существующем коде **не трогаем** — это чужой контур.

## 9. Флаги и автономность

### 9.1. Четыре независимых переключателя

Раздельно, как требует план:

| Флаг | Что включает |
|---|---|
| `ui` | доступ к новому интерфейсу |
| `ai` | запуск поручений |
| `autowrite` | автоматическое изменение данных без подтверждения |
| `outbound` | внешние отправки |

Каждый задаётся на трёх уровнях: **клиент → куратор → все**. Разрешение считается сверху вниз, ближайшее найденное побеждает. Отсутствие записи = выключено.

### 9.2. Политика автономности по типам действий

`care.autonomy_policy`: `scope` (клиент/куратор/глобально), `action_kind`, `mode` (`auto|confirm|human`). Слой инструментов читает её перед каждым действием. `outbound` при `care.env_marker.external_sends = false` не включается ничем — состояние базы сильнее флага и сильнее переменной окружения.

### 9.3. Один исполнитель на клиента

Требование плана: исключить одновременную обработку старым и новым процессом. Механизм: `care.cases.automation_owner` (`legacy|v2`). Правило:

- автоматизация нового кабинета работает только при `automation_owner = 'v2'`;
- переключение клиента в `v2` — отдельная операция, которая проверяет, что по нему нет выполняющихся заданий старого контура;
- при возврате в `legacy` новые задания не создаются, текущие доводятся или отменяются.

Поскольку сегодня у кураторов автоматизаций нет вовсе (аудит, блок 13), конфликт возможен только по отправкам сообщений — и он закрыт тем, что отправка идёт через `outbox` с проверкой владельца.

## 10. Перенос данных и возврат

### 10.1. Перенос (только подготовка)

Скрипт `scripts/care/backfill.ts`, четыре режима: `--preview` (ничего не пишет, печатает отчёт), `--apply`, `--verify`, `--report`.

Что переносится в `care.*` из `public.*`:

| Из | В | Правило |
|---|---|---|
| `clients` (активные) | `care.cases` | цикл = `expected_offer_month`, если пусто — текущий учебный год, помечается как предположение |
| `clients.project_data` | `care.facts` + `fact_sources(kind='manual')` | каждое поле — факт со статусом `confirmed` и датой «неизвестна» |
| `deals.custom_fields` | `care.facts` + `fact_sources(kind='quiz')` | статус `proposed`; расхождение с профилем создаёт `care.conflicts` |
| `client_universities` | `care.shortlists` версия 0 | статусы сохраняются |
| `client_documents` | `care.documents` версия 1 | файлы не копируются, ссылка на существующий путь |
| `clients.roadmap_data` | `care.plans` версия 0 + задачи без ответственных | ответственный проставляется вручную |

Свойства: идентификаторы и связи сохраняются; повторный запуск не создаёт дублей (ключ переноса `source_table:source_id`); после — сверка количеств и отчёт о непереносимом (свободный текст в `notes`, неоднозначные поля jsonb).

**Тестовая база поверх рабочей не переносится никогда.** Направление переноса проверяется предохранителем: источник — `public.*` той же базы, куда пишем.

### 10.2. Возврат

Возврат — это **остановка нового процесса**, а не откат данных. Так и описывается:

1. Снять флаги `ai`, `autowrite`, `outbound` (немедленно, без выкладки).
2. Отменить невыполненные задания; выполняющиеся довести или остановить по кнопке.
3. Снять флаг `ui` — кураторы возвращаются в старый кабинет.
4. Данные, накопленные новым кабинетом, остаются в `care.*` и не теряются.
5. Если нужно, чтобы важное было видно в старом интерфейсе — разово включить синхронизацию подтверждённых фактов в `clients.project_data` (6.6) и после этого выключить.

**Что необратимо:** отправленное сообщение. Отключение флага его не вернёт. Также необратимо удаление файла (у нас файлы не удаляются — именно поэтому). Всё остальное восстановимо: схему `care` можно удалить целиком, `public` останется нетронутой.

## 11. Приёмка изоляции

Отдельные проверки, которые должны падать, если изоляция нарушена (пункт 7 плана):

| Проверка | Как устроена | Ожидание |
|---|---|---|
| Запись в рабочие таблицы невозможна | ключом `CARE_DB_KEY` выполнить `update public.clients set name=…` | `permission denied for table clients` |
| Чтение закрытых таблиц невозможно | тем же ключом `select from public.payments` | `permission denied` |
| DDL невозможен | тем же ключом `create table public.x(...)` | отказ |
| Service-role в коде кабинета отсутствует | поиск `SUPABASE_SERVICE_ROLE_KEY` в `lib/care/*`, `app/care/*` | ни одного вхождения |
| Миграция, трогающая `public` | прогнать `scripts/care/check-sql.ts` на заведомо плохом файле | отказ применить |
| Сообщение реальному клиенту невозможно | попытка отправки при `external_sends = false` | строка `suppressed` в `outbox`, наружу ничего |
| Рубильник не переставить деплоем | изменить переменную окружения, не трогая базу | отправки остаются выключены |
| Прямой импорт `lib/telegram.ts` из `lib/care/*` | правило ESLint | сборка падает |
| Задание в боевой очереди невозможно | поиск обращений к `seo.jobs` в `lib/care/*` | ни одного |
| Синтетика не попала в `public` | `select count(*) from public.clients` до и после наполнения | число не изменилось |
| Чужой клиент | вызов операции от куратора без прав | отказ, запись в журнал |
| Повтор события | тот же вебхук дважды | одно задание, одно предложение |
| Устаревшее подтверждение | изменить факт после подготовки предложения | применение отклонено со статусом `stale` |

## 12. Что осталось решить (влияет на схему)

1. **Второй ответственный** — `care.case_members` заложен, но нужен ли он в интерфейсе на пилоте.
2. **Цикл поступления** — правило определения года при переносе: брать `expected_offer_month`, спрашивать куратора или ставить текущий.
3. **Плательщик и студент** — разделять ли сейчас. Если да, в `care` добавляется `persons` и `case_persons`; позже это дороже.
4. **Пароли от порталов вузов** — оставить как есть в `client_universities`, шифровать или убрать из нового интерфейса.
5. **Обратная синхронизация в `project_data`** — нужна ли на пилоте или достаточно, чтобы куратор работал только в новом кабинете.
6. **Порог «авто»** — какие типы действий вообще допускаются в режиме `auto` на пилоте.

## 13. Риски и что их держит

| Риск | Контроль |
|---|---|
| Случайная запись в рабочие таблицы | роль `care_app` без прав записи в `public` + запрет service-role в коде кабинета + проверка миграций `check-sql.ts` |
| Случайная отправка клиенту | единственная дверь `outbound.ts` + рубильник в базе (не в переменной) + подтверждение по `content_hash` + запрет импорта + полоса в интерфейсе |
| Новый код попал в боевой деплой | ветка `feat/curator-v2` не сливается в `main`; боевой Vercel собирает только `main` |
| Перезапуск API при добавлении схемы в Exposed schemas | делается в согласованное время, прежнее значение записано, возврат одной строкой (2.8) |
| Синтетические данные видны кураторам | синтетика только в `care.*`, старый кабинет схему не читает |
| Нагрузка нового кабинета мешает SEO | отдельная очередь, отдельный воркер, отдельное расписание |
| Данные разъехались между кабинетами | этап и карточка клиента остаются едиными; новый кабинет не пишет в поля старого без флага |
| ИИ выполнил инструкцию из документа | инструменты действия недоступны на шагах чтения внешнего текста; всё через предложение с цитатой |
| Дубль сообщения после сбоя | idempotency-ключ + отдельный статус «исход неизвестен» без автоповтора |
| Перерасход на модели | резерв бюджета до вызова, дневной потолок, отдельный ключ |
