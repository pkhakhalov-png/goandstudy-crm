# Почему статьи «молчат» в Google — разбор 17.09.2026

Вопрос был такой: одна статья появилась в индексе сразу, остальные семь стоят
красным «Google не видел адрес». Что сломалось?

Короткий ответ: с сайтом и со статьями всё в порядке. В индексе не одна статья,
а четыре. Врёт экран `/admin/seo/indexation` — по трём независимым причинам.

---

## 1. Что на самом деле

Спросил URL Inspection API напрямую, обе формы адреса, 17.09.2026 около 11:00 UTC.

| статья | реальный ответ Search Console |
|---|---|
| стоимость обучения в чулалонгкорне | **в индексе**, обход 16.09 16:27 |
| что делать если не поступил в зарубежный вуз | **в индексе**, обход 16.09 20:31 |
| как живут студенты за границей общежитие | **в индексе**, обход 16.09 20:29 |
| поступление в сша | **в индексе**, обход 16.09 19:41 |
| как получить грант на обучение в китае | «Обнаружена, не проиндексирована» — взята из sitemap, ждёт очереди |
| магистратура в австрии | Google адрес ещё не знает |
| консультант по образованию за рубежом | Google адрес ещё не знает |
| высшее образование в австрии | вышла сегодня, проверки ещё не было |

Технически со стороны сайта всё чисто:

- все восемь адресов есть в `https://goandstudy.com/sitemap.xml` (170 адресов всего);
- robots.txt ничего не закрывает, sitemap в нём указан;
- страницы отдают 200, адрес без слэша даёт 301 на адрес со слэшем;
- у проиндексированных `robots: ALLOWED`, `indexing: INDEXING_ALLOWED`,
  `fetch: SUCCESSFUL`, канонический адрес совпадает с нашим;
- Google пришёл именно по sitemap (`referringUrls: [".../sitemap.xml"]`).

**Про «одна появилась супер быстро».** Она не быстрее остальных. Чулалонгкорн
обошли 16.09 в 16:27, остальные три — тем же вечером, в 19:41–20:31. Проверка
конвейера прошла 16.09 в 16:59 и попала ровно между: одну застала уже в индексе,
остальные — ещё нет. Разницы в скорости индексации между статьями нет вообще,
есть разница в моменте, когда мы смотрели.

## 2. Три причины, почему экран показывает другое

### 2.1. Проверяем не тот адрес

`lib/seo/index-status.ts:34-43`

```ts
const first = await inspectUrl(bare)                 // адрес без слэша
if (!first.checked || first.verdict === 'PASS') return { ...first, url: bare }
const second = await inspectUrl(slashed)             // адрес со слэшем
if (second.checked && second.verdict === 'PASS') return { ...second, url: slashed }
return { ...first, url: bare }                       // ← сюда уходит вся правда
```

Сайт отвечает 301 с адреса без слэша, и для новых статей Google знает только
вариант со слэшем. Мы спрашиваем сначала бесслэшевый, получаем «URL неизвестен
Google», потом спрашиваем правильный — и берём его ответ, **только если он PASS**.
Любой другой содержательный ответ («Обнаружена, не проиндексирована»,
«Просканирована, не проиндексирована», «Страница с переадресацией») выбрасывается,
и на экран уходит «URL неизвестен» от адреса, которого не существует.

Живой пример на сегодня — «как получить грант на обучение в китае»:

```
/blog/kak-poluchit-grant-obuchenie-kitae   → NEUTRAL | URL неизвестен Google   ← показываем это
/blog/kak-poluchit-grant-obuchenie-kitae/  → NEUTRAL | Обнаружена, не проиндексирована
                                             sitemap: ["https://goandstudy.com/sitemap.xml"]
```

То есть статья благополучно найдена Google из sitemap и стоит в очереди, а экран
красит её в красное «Google не видел адрес» — самый пугающий из возможных ярлыков
(`app/admin/seo/indexation/page.tsx:27`).

Комментарий в коде («в индексе Google держит вариант БЕЗ слэша») верен для старых
страниц сайта — они действительно отвечают PASS на бесслэшевую форму. Для новых
статей конвейера он неверен.

### 2.2. Данные протухают на день-два

`lib/seo/steps-article.ts:786-788`

```ts
const wait = meta.index_check?.verdict === 'PASS' ? 14 * 864e5 : 2 * 864e5
if (Date.now() - last < wait) continue
```

Непроиндексированную статью перепроверяем не чаще раза в двое суток. Последняя
проверка трёх статей была 16.09 в 16:59; Google обошёл их в тот же вечер, уже
после проверки. Запуск шага в 22:48 того же дня проверил ровно ноль статей:

```
job #825  article_index_check  done  16.09 22:48  result={"checked":0,"newly_indexed":[]}
```

Все восемь отсеклись правилом двух дней. Следующая настоящая проверка — 18.09.
Для свежей статьи, где нас как раз интересует день попадания в индекс, шаг в два
дня слишком крупный: он гарантированно промахивается мимо события.

Дополнительно: проверка статьи, выпущенной сегодня, поставлена на завтра
(`job #865 next_run_at = 2026-09-18T09:31`, ставится в `app/api/seo/publish/result/route.ts:91`),
поэтому в таблице у неё честное «не проверяли».

### 2.3. Новых статей нет в `seo.pages`

`lib/seo/steps-article.ts:793`

```ts
const { data: page } = await seo.from('pages').select('id')
  .eq('normalized_url', url.replace(/\/$/, '')).maybeSingle()
if (page?.id) await saveIndexStatus(seo, page.id, res)   // ← у новых статей page нет
```

В `seo.pages` 220 строк, самая свежая заведена **09.09.2026**. Таблицу заполняет
только обход сайта (`lib/seo/crawl.ts`), а обход не является шагом конвейера —
среди зарегистрированных шагов его нет, его запускают руками скриптом.

Последствия:

- `saveIndexStatus` для статей конвейера молча ничего не делает;
- `index_status` для них не заводится, `first_indexed_at` не пишется — колонка
  «в индексе с» пустая даже у проиндексированных;
- таблица на экране падает на запасной источник — снимок `meta.index_check`
  в версии статьи (`app/admin/seo/indexation/page.tsx:113,126-131`), а он
  обновляется только шагом из пункта 2.2;
- статьи не участвуют в общей доле индексации по сайту и в блоке «свежие
  страницы»: там всё считается по `pages`.

Отсюда же «дней 0» у чулалонгкорна: `first_indexed_at` взялся не из `index_status`,
а из `articles.indexed_at`, который поставили в момент удачной проверки.

## 3. Что предлагаю чинить

По убыванию отдачи:

1. **Спрашивать слэш-форму первой и брать содержательный ответ, а не только PASS.**
   `lib/seo/index-status.ts`. Правило простое: если один из двух ответов говорит
   что-то осмысленное (PASS, «обнаружена», «просканирована», «переадресация»), а
   второй — «URL неизвестен», показываем первый. Это снимает ложное красное
   «Google не видел адрес» и возвращает полезное «знает, но не взял».

2. **Заводить страницу в `pages` при публикации статьи.** Тогда история
   индексации, дата попадания в индекс и общий процент по сайту начнут работать
   сами, без ручного обхода. Альтернатива — сделать обход шагом конвейера, но это
   дороже и решает ту же задачу окольным путём.

3. **Свежую непроиндексированную статью проверять раз в сутки, а не раз в двое.**
   Например: моложе 14 дней и не в индексе — сутки; дальше — двое; в индексе —
   две недели. Иначе момент попадания в индекс ловится с опозданием на день-два,
   и «дней до индекса» систематически завышен.

4. **Поправить подпись под таблицей.** Сейчас там написано, что для свежей статьи
   одна-две недели ожидания — норма. По факту конвейер получает индекс за сутки:
   четыре из восьми статей проиндексированы, самая старая из них вышла 13.09.
   Ожидание стоит переписать по фактическим данным, когда накопится история.

### Про дубль версии — честно

Причина падения `article_fix` до конца не доказана. Данные не сходятся с простой
гонкой: цикл подбора номера перечитывал максимум перед каждой из пяти попыток, и
все пять били в занятый номер. Починка гарантирует, что попытки расходятся
(каждая следующая берёт строго больший номер), а в журнал теперь попадает сам
ключ из ответа Postgres — `Key (article_id, version_no)=(7, 5) already exists`.
Если падение повторится, из журнала будет видно, какой именно номер не зашёл, и
тогда причина закроется окончательно.

Тайм-аут `gsc_daily` устранён отдельно, коммитом 5aeb5f4 (отбор запросов перенесён
в базу): задача #862 израсходовала попытки до того, как правка попала в main.
