# Цель для /goal: ни одного медленного запроса к базе

Ниже — формулировка цели с условиями завершения. Копируется целиком.

---

**Цель:** в CRM не осталось ни одного медленного обращения к базе — ни на
экранах админки, ни в фоновых шагах воркера. Результат доказан замерами до и
после, а не успешной сборкой.

## Готово, когда выполнено всё

1. **Каждый экран админки открывается за 700 мс или быстрее.** Замерено
   скриптом против боевой базы, не на глаз. Экранов восемнадцать: весь
   `/admin/*`, включая обе вкладки «Позиций» и «Индексации».

2. **Ни один отдельный запрос не превышает 200 мс.** Исключения допустимы, но
   каждое названо поимённо с объяснением, почему иначе нельзя.

3. **Нет ни одного места, где выдача обрезается молча.** Клиент Supabase
   отдаёт максимум 1000 строк: любой `select` без пагинации по растущей
   таблице — будущая тихая ложь в цифрах. Сейчас таких мест 103, проверить
   надо каждое.

4. **Нет запросов внутри циклов.** Известные: `app/admin/seo/effect/page.tsx:71`,
   `app/admin/seo/indexation/page.tsx:68`, `lib/seo/steps-article.ts` строки
   663, 921, 1081. Искать остальные.

5. **Цифры на экранах не изменились.** По каждому исправленному месту сверено
   «до» и «после». Если разошлись — объяснено, какая версия верна и почему.

6. **Каждая запись в базу проверяет ошибку.** В проекте находили `insert` без
   проверки `error`: операция падала, код шёл дальше и отчитывался об успехе.
   Это опаснее медленной страницы.

7. **Есть `scripts/perf-audit.ts`**, которым замеры повторяются одной командой.

8. **Есть итоговая таблица** «экран → было → стало → что сделано» со всеми
   восемнадцатью экранами и восемнадцатью шагами воркера.

9. **`npx tsc --noEmit` и `npm run build` проходят.**

## Чего делать нельзя

- Менять поведение экранов и показанные на них числа.
- Подключать платные сервисы, Redis, новые зависимости.
- Выполнять миграции самому: прямого доступа к DDL нет. Нужный SQL положить
  файлом в `supabase/migrations/` и сказать, что его применяют руками.
- Печатать значения секретов и перезаписывать `.env.local` целиком.

## Контекст, без которого замеры бессмысленны

Стек: Next.js 16 (App Router), Supabase без ORM, серверные компоненты читают
данные при каждом рендере. Фоновые шаги в `lib/seo/steps*.ts`, запускает
`app/api/seo/tick`.

Размеры таблиц: `seo.gsc_daily` 190 498 строк и растёт на полторы тысячи в
сутки, `seo.gsc_page_daily` 17 956, всё остальное — сотни строк и таким
останется. Оптимизировать таблицу на 68 клиентов смысла нет.

Образцы уже исправленных мест, на которые стоит равняться:
`loadPageDays` в `lib/seo/gsc-agg.ts` — чтение пачками параллельно;
`flowSnapshot` в `lib/seo/flow.ts` — тяжёлый расчёт вынесен в воркер, экран
читает готовое.

## Как не обмануться

Не доверять догадкам по коду: сегодня «очевидно тяжёлый» запрос отработал за
130 мс, а безобидный на вид — за три секунды. Сначала замер, потом правка,
потом замер снова.

Если какое-то место нельзя ускорить без смены схемы — сказать прямо и оставить
в списке нерешённого. «Оптимизировано» без цифр не считается результатом.
