# Конвейер: запуск, остановка, разбор поломок

Всё, что нужно, когда что-то пошло не так. Порядок действий, а не теория.

---

## 1. Включить и выключить поток

**В CRM:** `/admin/seo/articles` → блок «Поток статей» → тумблер.

Там же настраивается ритм (статей в неделю) и предел на вычитке. Предел важнее
ритма: если незакрытых статей больше предела, конвейер останавливается сам и
пишет, почему.

**Остановить всё немедленно** — выключить тумблер. Уже запущенные задачи
доработают: они дешёвые и безвредные.

**Остановить вместе с текущей работой:**
```sql
update seo.jobs set status = 'failed', last_error = 'остановлено вручную'
 where status in ('pending', 'running') and step like 'article_%';
```

select id, step, status, runner, attempts, left(last_error, 120) as error, created_at

## 3. Задача застряла

С 17 сентября правило другое. Раньше очередь возвращала в работу всё, что
провисело в `running` дольше десяти минут, — и не могла отличить умершего
исполнителя от долгого шага. Теперь исполнитель раз в полминуты отмечается,
что жив, и решает именно это.

Сначала посмотреть, кто как себя чувствует:
```sql
select id, step, locked_by,
       round(extract(epoch from now() - heartbeat_at)) as сердце_сек,
       round(extract(epoch from lease_expires_at - now())) as аренда_осталось_сек,
       fencing_token, handler_version
  from seo.jobs where status='running' order by id;
```

Как читать:

| Что видно | Что это значит |
|---|---|
| `сердце_сек` меньше 180 | исполнитель жив, шаг идёт. Ничего не делать |
| `сердце_сек` больше 180 | исполнитель молчит — очередь вернёт задачу сама при ближайшем захвате |
| `heartbeat_at` пустой, `fencing_token` пустой | задачу взял агент публикации мимо `claim_jobs`. Для неё работает прежняя мерка: десять минут по `locked_at` |

Ускорить возврат вручную можно, но осторожно: если исполнитель на самом деле
жив, он доработает шаг и попробует записать результат. Записать не даст fencing
— номер выдачи у него станет старым, — но работа будет сделана дважды и
дважды оплачена.
```sql
update seo.jobs set status='pending', locked_at=null, locked_by=null,
       lease_expires_at=null where id = <id>;
```

**Если возвращать стало нечего, а задачи всё равно висят** — правило могли
выключить. Проверить:
```sql
select value from seo.settings where key='lease_recovery';   -- должно быть true
```

## 3а. Всё вернулось в очередь разом

Признак: десятки задач одновременно ушли из `running` в `pending`, счётчик
попыток у всех вырос на единицу.

Значит исполнители перестали отмечаться все сразу — либо упали, либо потеряли
связь с базой. Чинить надо не очередь, а исполнителей.

Аварийный выключатель — вернуть прежнее правило по `locked_at` без миграции:
```sql
update seo.settings set value = to_jsonb(false) where key='lease_recovery';
```
Это возвращает поведение до 17 сентября: возврат через десять минут, долгие
шаги снова опасны. Мера временная, на разбор.

## 4. Задача упала

```sql
select step, attempts, max_attempts, last_error from seo.jobs where status='failed' order by id desc;
```

Как читать ошибку:

| Текст | Что значит | Что делать |
|---|---|---|
| `no credits remaining`, `quota` | кончились деньги у поставщика | пополнить счёт, затем перезапустить |
| `invalid_client`, `401` | ключ не работает | заменить ключ, перенести на Vercel |
| `spawn ssh ENOENT` | задачу взял не тот исполнитель | применить миграцию `20260911120000_jobs_runner.sql` |
| `429 rate limit`, `fetch failed` | временное | повторится само |
| `слаг уже занят` | статья с таким адресом есть | публиковать в режиме обновления |

**Перезапустить упавшую задачу:**
```sql
update seo.jobs set status='pending', attempts=0, next_run_at=now(), last_error=null
 where id = <id>;
```

## 5. Публикация

Публикует **агент на сервере**, не CRM. Порядок при разборе:

```bash
# 1. Жив ли агент
ssh root@72.56.242.202 "tail -20 /var/log/gs-publish.log"

# 2. Стоит ли задача
#    select * from seo.jobs where step='article_publish_blog' order by id desc limit 3;

# 3. Что реально лежит на сервере
ssh root@72.56.242.202 "ls -l /var/www/html/wordpress/wp-content/themes/goandstudy/inc/blog-articles/<slug>.html"
```

**Сухой прогон** — кнопка в CRM показывает, какие файлы куда уедут, ничего не
трогая. Пользуйтесь им перед всякой непонятной публикацией.

## 6. Откат публикации

Перед каждой перезаписью агент делает копии:

```bash
ssh root@72.56.242.202 "ls -lt /var/www/html/wordpress/wp-content/themes/goandstudy/inc/blog-articles/<slug>.html.bak.* | head"

# вернуть тело статьи
ssh root@72.56.242.202 "cp <файл>.bak.<время> <файл>"

# вернуть реестр
ssh root@72.56.242.202 "ls -lt /var/www/html/wordpress/wp-content/themes/goandstudy/inc/blog-data.php.bak.*"
```

После отката **обязательно** поднять флаг пересборки, иначе страница останется
прежней:
```bash
ssh root@72.56.242.202 "grep -o 'goandstudy_seed_v[0-9]*' /var/www/html/wordpress/wp-content/themes/goandstudy/functions.php | tail -1"
```
Далее заменить номер на следующий в `functions.php`.

**Полный откат темы** (если сломана не одна статья):
```bash
ssh root@72.56.242.202 "ls -lt /root/backups/theme-*.tgz | head -3"
ssh root@72.56.242.202 "tar xzf /root/backups/theme-<метка>.tgz -C /var/www/html/wordpress/wp-content/themes"
```

## 8. Статистика GSC выглядит странно

Сначала — не поломка ли это импорта:

```sql
select value from seo.settings where key = 'gsc_import_health';
```

Смотреть `lastDayRows`: за сутки сайт показывается по сотне с лишним адресов.
Если там десятки — часть строк не доехала. Поле `suspicious` появляется, когда
сторож сам заметил неладное.

**Добрать данные вручную:**
```bash
npx tsx scripts/seo-gsc.ts 2026-05-01 2026-09-08
```

Повторный импорт безопасен: строки перезаписываются, а не складываются.

## 9. Индексация

```bash

npx tsx scripts/seo-index-check.ts       # только наши статьи
```

Экран `/admin/seo/indexation` показывает то же самое без терминала.

Помнить: **уведомление ≠ индексация**. IndexNow принял — значит Яндекс узнал
об адресе, не более. Google заявок на индексацию не принимает вовсе. Первое
обнаружение в индексе — не точная дата индексации, а дата, когда мы это
увидели.

## 10. Ключи и где они живут

| Переменная | Зачем | Где настраивать |
|---|---|---|
| `ANTHROPIC_API_KEY` | тексты | `.env.local` и Vercel → Environment Variables |
| `FAL_KEY`, `IMAGE_PROVIDER` | картинки | там же |
| `GSC_CLIENT_ID/SECRET/REFRESH_TOKEN` | статистика и индексация | там же; токен обновляется `scripts/seo-gsc-auth.ts` |
| `WP_BRIDGE_SECRET` | мост WordPress | сервер: `/root/gs-bridge-secret.txt` |
| `SEO_PUBLISH_TOKEN` | агент публикации | сервер: `/etc/gs-publish-agent.env` |
| `EMBEDDING_API_KEY` | векторы | `.env.local` и Vercel |
| `INDEXNOW_KEY` | уведомление поисковиков | публичный, лежит файлом в корне сайта |

**Правило:** ключи не печатать в терминал и не вставлять в переписку. Локальный
файл целиком не перезаписывать — дописывать строкой.

Копии локального файла: `~/Desktop/env-backup/`.

## 11. Режим приложения Google

Постоянный токен Search Console живёт **семь дней**, пока приложение в режиме
Testing. Это правило Google, а не наша ошибка настройки: непереведённое
приложение считается черновиком.

Проверить здоровье доступа:
```bash
npx tsx scripts/seo-gsc-health.ts
```

**Перевести в рабочий режим (делается один раз, руками):**

1. `console.cloud.google.com/auth/audience` — выбрать проект `goandstudy-seo`.
2. Раздел **Audience**, кнопка **Publish app**.
3. Google спросит подтверждение — согласиться.
4. Статус сменится с «Testing» на «In production».

Проверки Google при этом не требуется: мы запрашиваем только доступ к своему
же ресурсу в Search Console, а не к данным пользователей. Экран согласия
увидит только владелец аккаунта.

После перевода токен перестаёт протухать. Если этого не сделать, через неделю
ночной импорт упадёт с `invalid_grant`, и придёт уведомление о поломке —
чинить придётся повторным `npx tsx scripts/seo-gsc-auth.ts`.

## 12. Уведомления о поломках

Раз в час конвейер проверяет себя и пишет в Telegram, если нашёл беду:
задача сдалась окончательно, задача висит дольше получаса, или за сутки не
завершилось ни одной задачи при включённом потоке.

Одно сообщение на одну беду, повтор не раньше чем через шесть часов — иначе
уведомления начнут игнорировать.

Куда пишет: `SEO_ALERT_CHAT_ID`, а если её нет — в чат заявок. Отдельная
переменная лучше: беда конвейера не касается продавцов.

Посмотреть, что система считает бедой прямо сейчас:
```bash
npx tsx -e "import('./lib/seo/alerts').then(async m => console.log(await m.collectAlerts((await import('./lib/supabase/server')).createAdminClient())))"
```

## 14. Бюджет исчерпан

Признак: шаги перестали начинаться, в логе `бюджет исчерпан: на шаг нужно N $`.
На экране «Конвейер» остаток красный.

Это не поломка, а защита: резерв берётся ДО платного вызова, и когда свободных
денег нет, шаг не начинается вовсе. Лучше встать, чем потратить сверх лимита.

Посмотреть, куда ушло:
```sql
select * from seo.budget_left();

select role, provider, model, count(*), round(sum(cost)::numeric, 2) as потрачено
  from seo.runs
 where started_at > now() - interval '24 hours'
 group by 1,2,3 order by потрачено desc;
```

Поднять предел (суточный или месячный):
```sql
update seo.settings set value = to_jsonb(50) where key='budget_daily_usd';
```

**Если остаток не сходится с ощущениями** — скорее всего висят резервы под
вызовы с неизвестным исходом. Они не освобождаются намеренно: провайдер мог
сделать работу и списать деньги, а мы не узнали. Посмотреть их:
```sql
select b.id, b.amount, b.role, b.created_at, r.status, r.error
  from seo.budget_reservations b
  left join seo.runs r on r.id = b.run_id
 where b.state='held' and b.created_at < now() - interval '1 hour'
 order by b.created_at;
```
Разобравшись по счёту провайдера, закрыть вручную:
```sql
-- деньги списаны: закрыть фактической суммой
select seo.settle_reservation(<id резерва>, <id вызова>, <сумма>);
-- вызова не было: отпустить
update seo.budget_reservations set state='released', settled_at=now() where id=<id>;
```

## 15. Отозван или протух токен

Признак: шаг падает с `401`, `invalid_api_key`, `unauthorized`. Классификатор
считает такую ошибку окончательной и повторять не будет — это правильно,
повторы с мёртвым ключом только жгут попытки.

| Чей ключ | Где заменить | Что встанет без него |
|---|---|---|
| Anthropic | Vercel env `ANTHROPIC_API_KEY` | производство статей целиком |
| Voyage | `EMBEDDING_API_KEY` | проверка каннибализации в починке |
| fal | `FAL_KEY` | картинки, а без обложки статья не публикуется |
| GSC | `GSC_REFRESH_TOKEN`, см. раздел 11 | импорт статистики и проверка индексации |
| Мост WordPress | `WP_BRIDGE_SECRET` + `wp-config.php` на сервере | публикация на сайт |
| Агент публикации | `/etc/gs-publish-agent.env` на сервере | публикация на сайт |

После замены в Vercel нужен редеплой — переменные окружения читаются при
сборке функции, а не на каждый запрос.

Отзыв ключа одного провайдера не должен ронять остальное. Если уронил —
это дефект, и его надо записать, а не обойти.

## 16. Откат миграции

Все миграции обёрнуты в транзакцию: либо применилась целиком, либо не
применилась вовсе. Наполовину применённого состояния не бывает.

Порядок отката, от простого к сложному:

**1. Настройкой, без SQL-структуры.** Так откатываются поведенческие правила:
```sql
-- вернуть прежнее правило возврата задач
update seo.settings set value = to_jsonb(false) where key='lease_recovery';
-- вернуть выбор статьи по номеру
insert into seo.settings (key, value) values ('autopublish_order', to_jsonb('legacy'))
  on conflict (key) do update set value = to_jsonb('legacy');
```

**2. Файлом отката.** У миграций, которые меняли функции, рядом лежит
`*.rollback.sql` с текстом или указанием, откуда взять прежнюю версию.

**3. Колонки не удаляются.** В них уже могут лежать данные текущих выдач, и
PRD §14 требует отката без удаления. Лишняя колонка ничему не мешает.

Чего делать нельзя: править функцию прямо в SQL Editor, не занося правку в
миграцию. Через неделю никто не вспомнит, что в базе не то, что в репозитории,
и следующая миграция ляжет поверх неизвестного состояния.

## 17. Упал сервер с воркерами

На 17 сентября отдельного сервера с воркерами ещё нет: модели зовёт функция
на Vercel, файлы темы пишет агент на сервере сайта. Раздел написан заранее,
чтобы не писать его в момент аварии.

**Что не встанет.** Сайт и опубликованные статьи живут на сервере сайта и от
воркеров не зависят. CRM живёт на Vercel. Падение сервера воркеров
останавливает производство новых статей, но не ломает то, что уже вышло.

**Что произойдёт само.** Задачи, которые воркеры держали, вернутся в очередь,
когда перестанут отмечаться, — это 180 секунд после последнего удара. Ничего
чинить в очереди не нужно.

**Чего делать нельзя.** Поднимать второй экземпляр воркеров «на время» на
другой машине, не погасив первый. Если первый оживёт, обе копии возьмутся за
одну работу; от дублей защищает fencing, но деньги на повторные вызовы уйдут.

**Порядок:** поднять сервер → убедиться, что процессы стартовали → посмотреть
на экран «Конвейер»: возраст старейшей ждущей задачи должен пойти вниз.
