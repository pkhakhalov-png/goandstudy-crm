# ADR-0002. Аренда задачи, heartbeat и fencing

_Статус: принято. Реализация — E1._
_17 сентября 2026._

## Проблема

`seo.claim_jobs` при каждом вызове переводит в `pending` всё, что провисело в
`running` дольше десяти минут (`supabase/migrations/20260911120000_jobs_runner.sql:56`).

База не может отличить «воркер умер» от «шаг идёт дольше десяти минут», потому что
исполнитель никак не сообщает, что жив. Отсюда два последствия:

- долгая задача перезапускается, хотя работает — и делает работу дважды;
- пока это так, долгие задачи в очередь добавлять нельзя (PRD E1.4 прямо запрещает).

## Решение

Дополняем `seo.jobs` совместимыми миграциями, ничего не удаляя:

| Колонка | Зачем |
|---|---|
| `job_key` | логический ключ шага; уникален. Повторная постановка не создаёт вторую задачу |
| `lease_owner` | кто держит задачу сейчас |
| `lease_expires_at` | до какого момента аренда действительна |
| `heartbeat_at` | когда исполнитель в последний раз подтвердил, что жив |
| `fencing_token` | монотонный счётчик выдачи |
| `next_attempt_at` | когда можно пробовать снова |
| `handler_version` | версия обработчика, которая взяла задачу |

Существующие `locked_at` / `locked_by` / `next_run_at` остаются и продолжают
работать: PRD E1.3 требует использовать аналоги, если они есть, а не дублировать.
`lease_owner` и `heartbeat_at` — это то, чего у них нет.

**Правило возврата меняется.** Задача возвращается в очередь не по возрасту
`locked_at`, а по истечении `lease_expires_at` при отсутствии свежего `heartbeat_at`.
Долгий шаг с живым heartbeat не трогаем.

**Fencing обязателен.** При каждой выдаче счётчик растёт. Воркер, чья аренда
истекла, при попытке записать результат получает отказ: его токен меньше текущего.
Без этого «воскресший» воркер затрёт работу нового — а это тот самый дубль, который
MVP обязан исключить.

## Как проверяем

Тесты из PRD E1, все обязательные:

1. `kill -9` посреди задачи → задача вернулась, не продублировалась, результат
   старого воркера после выдачи нового токена не записался.
2. Задача длиннее 10 минут с heartbeat не перезапущена.
3. Vercel не захватил SSH-задачу; неизвестный обработчик не забрал задачу.
4. Параллельные резервы бюджета не дали превысить лимит.

## Порядок выкатки

Строго `expand → backfill → verify → enable`. Сначала колонки добавляются и
заполняются, старая логика продолжает работать. Переключение правила возврата —
отдельным шагом под флагом, с возможностью вернуться, не удаляя колонок.

Пока переключение не сделано, долгие задачи в очередь не добавляются.
