# Финансовый модуль: карта интеграции с существующей CRM

Это результат нулевого этапа из PRD (§12.1, §18) — обязательного аудита до
написания кода. PRD писался без доступа к репозиторию и честно предупреждает,
что названия сущностей в нём предложенные. Ниже — что в CRM есть на самом деле.

Данные сняты с боевой базы 15 сентября 2026 года.

---

## 1. Что в CRM уже есть про деньги

| Таблица | Строк | Что это на самом деле |
|---|---:|---|
| `payments` | 174 | График платежей клиента: `plan_date`/`plan_sum`, `is_paid`, `fact_date`/`fact_sum`. Оплачено 136 на **10 546 996 ₽**, период 12.02.2026 — 14.09.2026 |
| `expenses` | 163 | Выплаты по конкретному клиенту. Статей ровно две: `curator` (103 записи, 1 240 000 ₽) и `salesperson` (60 записей, 1 436 556 ₽). Статусы `paid` 110 / `pending` 53 |
| `fixed_expenses` | 2 | «Офис» и «SEO». **Без сумм** — только название, период и статья. То есть постоянные расходы в деньгах не учитываются вообще |
| `invoices` | 20 | Ссылки на оплату Т-Банка: сумма, `status` (`CONFIRMED`), `payment_id`, `payment_url` |
| `clients` | 68 | Клиенты, `service_type`, `months`, `commission_per_payment` |
| `users` | 41 | Роли: `admin` 1, `rop` 1, `salesperson` 9, `curator` 6, `client` 24 |
| `curators` | 10 | Справочник кураторов, у части есть `telegram_id` |

### Чего нет совсем

Ни одной из вещей, на которых стоит весь PRD:

- **счетов и валют** — нигде нет понятия «где лежат деньги»; всё неявно рублёвое;
- **остатка** — ни расчётного, ни начального. Цифры на экранах — это суммы по
  клиентским строкам, а не деньги компании;
- **движений со знаком**, переводов между счетами, комиссий;
- **потоков основателей** — взносов, выводов, оплат из личных, возмещений;
- **возвратов** как отдельного факта;
- **истории исправлений и отмен** денежных сумм, аудита;
- **сверки с банком**;
- **идемпотентности** — защиты от повторной записи одной операции.

### Вывод

**Того, что PRD называет финансовым реестром, в CRM нет.** Есть клиентский
учёт: сколько клиент должен и сколько ему выплатили исполнители. Это ценная
часть, но она отвечает на вопрос «как идёт клиент», а не «сколько у компании
денег и куда они ушли».

Поэтому денежное ядро заводится новым — и одновременно существующие оплаты
подключаются к нему мостом, чтобы не получилось двух реестров (PRD §12.1).

## 2. Требование PRD → что есть → что делаем

| Требование | Существующее | Решение |
|---|---|---|
| Счета, валюты, начальные остатки | нет | Новая таблица `finance.accounts`. Валюта — перечисление, RUB/USD |
| Операция с движениями по счетам | нет | `finance.transactions` + `finance.movements` со знаком |
| Остаток счёта | нет | Считается из журнала движений (`finance.account_balances`), не хранится числом |
| Оплата клиента | `payments` (174) | Мост: `transactions.crm_payment_id` — уникальная ссылка. Оплата, отмеченная в карточке клиента, даёт одно движение и ровно одно |
| Выплата куратору/продажнику | `expenses` (163) | Мост: `transactions.crm_expense_id`, тоже уникальный |
| Постоянные расходы | `fixed_expenses` без сумм | Становятся плановыми обязательствами `finance.obligations` с суммой, сроком и статусом |
| Категории расходов | `article`: только `curator`, `salesperson` | Новый справочник `finance.categories`; старые две статьи отображаются в «Кураторы и сопровождение» и «Зарплаты» |
| Контрагенты | `curators`, `users`, поле `who` строкой | `finance.counterparties` со ссылками на существующие записи + псевдонимы. Людей не дублируем |
| Клиент, договор | `clients`, `deals` | Прямые ссылки из операции, без копий |
| Планы и частичные оплаты | `payments.plan_*`, `expenses.plan_*` | `finance.obligations` + `finance.settlements`; старые планы остаются на месте |
| Права на финансы | роли CRM | Отдельная таблица `finance.access`: по PRD §5 доступ к CRM прав на деньги не даёт |
| Телеграм | бот сделок (`TELEGRAM_BOT_TOKEN`), бот записей (`TELEGRAM_BOOKINGS_BOT_TOKEN`) | **Третий бот** со своим вебхуком. Смешивать с ботом сделок нельзя: тот слушает клиентские чаты |
| Идемпотентность | нет | `finance.idempotency_keys` + уникальность `update_id` события Telegram |
| Аудит | `deal_activities` только по сделкам | `finance.audit_events` |

## 3. Единственный источник и граница запуска

**Единый реестр — `finance`.** Карточка клиента и бот пишут в него через один
сервис; второго денежного реестра не заводим.

Граница: владелец выбирает дату и время начала учёта и вводит остатки счетов
на этот момент.

- Всё, что **до** границы, — уже внутри начального остатка. `payments` и
  `expenses` за прошлое остаются историей клиента, но **повторно к остатку не
  прибавляются**. В базе это защищено триггером: движение раньше `opening_at`
  своего счёта не вставится.
- Всё, что **после** границы, порождает движение денег — один раз, по мосту
  `crm_payment_id` / `crm_expense_id`.

Практическое следствие, которое надо принять до запуска: чтобы оплата клиента
давала движение, у неё должен появиться **счёт**. Сейчас в `payments` его нет.
Варианта два: либо правило по умолчанию («рублёвая оплата → Т-Банк»), либо
выбор счёта в момент отметки «оплачено». PRD допускает оба; правило быстрее,
выбор честнее. Предлагаю правило плюс возможность переопределить.

## 4. Что придётся изменить в существующем коде

| Место | Изменение |
|---|---|
| `app/admin/payments/actions.ts` | При отметке «оплачено» с суммой и датой — вызов финансового сервиса, проведение поступления |

| `lib/telegram.ts` | Добавить третий бот; не трогать существующие два |
| `app/api/telegram/webhook` | Отдельный маршрут `/api/finance/telegram` — смешивать нельзя |

## 5. Порядок работ

| Этап | Содержание | Состояние |
|---|---|---|
| 0 | Аудит и эта карта | **готово** |
| 1 | Схема БД: `supabase/migrations/20260915000000_finance_core.sql` | **написана, не применена** |
| 2 | Финансовое ядро: сервис проведения, отмены, исправления, переводы, остатки, контрольные суммы | следующий шаг |
| 3 | Раздел «Финансы» в CRM: обзор, операции, счета, календарь, сверка, отчёты | после ядра |
| 4 | Мост с `payments`/`expenses` + перенос истории без задвоения | после ядра |
| 5 | Телеграм: привязки, группа, текстовый ввод, уточнения, идемпотентность | после раздела |
| 6 | Голос, пакетный ввод, вопросы к отчётам | последним |

Порядок из PRD §18 и он же здравый: сначала деньги должны сходиться без ИИ,
потом к ним подключается распознавание.

## 6. Что нужно от владельца, без чего этап 2 не запускается

Это пункты §20 PRD. Первые четыре блокируют, остальные — нет.

1. **Дата и время начала учёта.** Предлагаю 1 октября 2026, 00:00 МСК — начало
   месяца проще сверять. Можно любую другую.
2. **Остатки на эту границу:** сколько на счёте Т-Банка в рублях и сколько на
   долларовой карте.
3. **Название долларового счёта** (банк не нужен, нужно имя для интерфейса).
4. **Кто из пользователей CRM — основатели**, и их telegram: привязка делается
   одноразовой ссылкой, id берётся автоматически.
5. Часовой пояс — предлагаю Europe/Moscow.
6. Справочный курс RUB за 1 USD на старте.
7. Токен нового бота от @BotFather и закрытая группа, куда его добавить.
8. Провайдер распознавания речи. На аккаунте OpenAI сейчас **нет кредитов** —
   это выяснилось при генерации картинки для блога. Для голоса нужен либо
   пополненный OpenAI (Whisper), либо другой провайдер.

## 7. Честные оговорки

- **Модуль серверный, как SEO.** Схема `finance` доступна только `service_role`,
  права проверяются в коде по `finance.access`. Это соответствует тому, как
  устроен остальной проект, но это не RLS: ошибка в коде даст доступ, которого
  не должно быть. Если хотите строже — политики RLS поверх, отдельным шагом.
- **Схему нужно открыть в настройках.** Supabase отдаёт через API только схемы
  из списка Exposed schemas. `finance` туда нужно добавить руками, иначе
  приложение получит «schema not found».
- **`invoices` — потенциальный источник поступлений.** Двадцать записей со
  статусом `CONFIRMED` от Т-Банка означают, что деньги пришли. PRD запрещает
  банковские API, но это не банковское API, а наш же счёт по ссылке оплаты.
  Предлагаю обсудить после запуска ядра: это снимет часть ручного ввода.
- **`fixed_expenses` без сумм** — значит, постоянных расходов в деньгах никто
  не вёл. Первый месяц цифры будут выглядеть «слишком хорошими», пока офис,
  сервисы и реклама не начнут вноситься.
