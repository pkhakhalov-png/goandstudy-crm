# Аудит существующей системы (E0)

_17 сентября 2026. Выход этапа E0 по `PRD-content-engine-mvp`, раздел 4._

## Как читать

Каждое утверждение здесь либо подтверждено файлом и строкой, либо запросом к боевой
базе. Ничего не перенесено из `docs/seo-report.md`, `docs/seo-status.md` и прочих
отчётов без проверки — PRD отдельно предупреждает, что описание отчёта не является
схемой базы, и предупреждение оказалось оправданным (раздел 9).

Где утверждение проверить не удалось, так и написано. Раздел 10 — список того, что
осталось непроверенным.

## 1. Что это за система

Конвейер производства SEO-статей внутри CRM. Тема приходит из Search Console,
превращается в бриф, черновик, проверки, картинки; готовая статья кладётся файлом
в тему WordPress на сервере сайта. Темп — одна статья в сутки.

Схема `seo` в той же базе Supabase, что и CRM. Отдельного сервиса нет.

## 2. Проверенные факты о платформе

| Что | Значение | Где проверено |
|---|---|---|
| Next.js | 16.2.2 | `package.json` |
| React | 19.2.4 | `package.json` |
| Node (локально) | v24.14.1 | `node -v` |
| Очередь | `seo.jobs`, id `bigserial` | `supabase/migrations/20260908000001_seo_schema.sql:346` |
| Типы ID в схеме `seo` | `bigserial`/`bigint` везде; `uuid` только для ссылок на `users` | там же, `:77`, `:95`, `:204` |
| Расписание | `pg_cron` внутри Supabase → `pg_net` → HTTP | `20260908000003_seo_cron.sql:20` |
| Адрес тика | `https://crm.goandstudy.com/api/seo/tick`, ключ `settings.tick_url` | проверено в базе |
| Секрет тика | Supabase Vault, имя `SEO_TICK_SECRET` | `20260908000003_seo_cron.sql:28` |

**Инструмент миграций.** `supabase/config.toml` есть (`project_id = "goandstudy-crm"`),
но проект не залинкован: миграции применяются вручную через SQL Editor. То есть
файлы в `supabase/migrations/` — это журнал намерений, а не гарантия того, что
применено. Расхождения между файлами и базой возможны и одно найдено (раздел 8).

**Авторизация CRM.** `middleware.ts` проверяет сессию Supabase по cookie и роль из
таблицы `users`. Серверные действия дополнительно зовут локальный `assertAdmin()`
(`app/admin/seo/articles/actions.ts:10` и копия в `app/admin/clients/actions.ts:8`),
который требует `role = 'admin'`, после чего работа идёт через `createAdminClient()`
— то есть под `service_role` в обход RLS (`lib/supabase/server.ts:28`).

Маршруты `/api/seo/*` из проверки сессии исключены намеренно и имеют собственную
авторизацию по заголовку (`middleware.ts:50`).

**Где лежат секреты.** Четыре разных места, и это уже почти то разделение, которого
требует PRD E1.2:

| Где | Что там | Кто видит |
|---|---|---|
| Vercel env | ключи моделей, `SUPABASE_SERVICE_ROLE_KEY`, GSC, `WP_BRIDGE_SECRET` | всё приложение CRM |
| Supabase Vault | `SEO_TICK_SECRET` | только функция `seo.dispatch_tick()` |
| `/etc/gs-publish-agent.env` на сервере сайта | `CRM_URL`, `PUBLISH_TOKEN` | только агент публикации |
| `.env.local` | то же, что в Vercel, для локальных прогонов | машина разработчика |

Агент на сервере сайта намеренно не знает ничего, кроме одного узкого токена —
в коде прямо указана причина: «сервер ломали в июле и августе»
(`server-agent/gs-publish-agent.php:7`).

## 3. Кто реально исполняет задачи

Исполнителей три, и они разные по природе.

**Тик на Vercel** (`app/api/seo/tick/route.ts`). Просыпается от `pg_cron` раз в
минуту, берёт до 5 задач, работает не дольше 240 с при жёстком пределе платформы
300 с, остаток возвращает в `pending`. Делает всё, что требует моделей.

Запас времени почти исчерпан. В коде записаны замеры живого прогона (`:15`):

> бриф 122 c, черновик 189 c, проверки с починкой 209 c

Поэтому там же стоит защита: длинный шаг не начинается, если до конца бюджета
осталось меньше 230 с (`:19`). Двух независимых ревьюеров из PRD E2 в оставшиеся
90 секунд добавить нельзя.

**Агент на сервере сайта** (`server-agent/gs-publish-agent.php`). Крон раз в минуту,
спрашивает `/api/seo/publish/next`, пишет HTML в тему, отчитывается в
`/api/seo/publish/result`. Умеет ровно два дела: положить статью и вставить ссылку.

**Локальный воркер** (`scripts/seo-worker.ts`). Запускается руками, круглосуточным
сервисом не является — PRD E0.4 требует это зафиксировать, фиксирую.

**Непрерывность проверена.** За последние 72 часа задачи создавались в 71 часе из 72.
Статьи выходили без пропусков: 12, 13, 14, 15 и 16 сентября — по одной. То есть
существующий поток работает и требование «не деградировать» имеет измеримую базу.

## 4. Очередь: что уже есть

`seo.claim_jobs(p_worker, p_limit, p_runner)` — вторая перегрузка, старая
двухаргументная снята явно (`20260911120000_jobs_runner.sql:45`). Умеет:

- отбор по исполнителю: `any` / `vercel` / `agent` (`:47`, колонка `runner`);
- лимиты параллельности по дорожкам из `settings.worker_concurrency_by_lane`
  (в базе сейчас: production 3, crawl 3, freshness 2, gsc 1, index 1, attribution 1,
  autopilot 1);
- `FOR UPDATE SKIP LOCKED` — два исполнителя не возьмут одну задачу;
- фильтрацию по паузе прогона (`production_runs.status`).

`seo.complete_job` умеет fan-in по `group_key` и экспоненциальный backoff при
`retry` (`20260908000002_seo_functions.sql:115`).

**Терминальные статусы** (проверено по коду `complete_job`): `done`, `failed`,
`cancelled`. Не терминальные: `pending`, `waiting`, `running`, `awaiting_human`.
Исход `released` возвращает задачу в `pending` без штрафа и без продвижения fan-in.

## 5. Очередь: что сломано

**Возврат `running` по таймеру жив.** `claim_jobs` при каждом вызове переводит в
`pending` всё, что висит в `running` дольше 10 минут
(`20260911120000_jobs_runner.sql:56`). Аренды и heartbeat нет, поэтому отличить
«воркер умер» от «шаг идёт дольше десяти минут» база не может. PRD E1.4 требует это
убрать — требование обоснованное.

**Локальный воркер игнорирует маршрутизацию.** `scripts/seo-worker.ts:19` зовёт
`claim_jobs` без `p_runner`, из-за чего фильтр исполнителя отключается и локальная
машина может забрать задачу, предназначенную агенту сервера. Тик на Vercel передаёт
`p_runner: 'vercel'` правильно (`app/api/seo/tick/route.ts:114`), так что в бою
дыра не срабатывает — но при ручном прогоне сработает.

**Учёта расходов нет.** В `seo.jobs` есть колонка `cost`, и `complete_job` её
накапливает, но таблиц `runs`, `budget_reservations`, `cost_ledger` из PRD не
существует. Сколько стоит одна статья — сейчас неизвестно.

## 6. Реестр фактов: пусто

Схема под доказательства есть, данных нет.

| Таблица | Строк |
|---|---|
| `seo.claims` | 19 |
| `seo.claim_sources` | **0** |
| `seo.source_snapshots` | **0** |
| `seo.sources` | 1 |

Все 19 утверждений имеют `confidence = 'single_source'` и `status = 'active'`.
При этом `isBacked()` (`lib/seo/fact-gate.ts:44`) считает утверждение подтверждённым,
только если `confidence = 'confirmed'` **или** есть хотя бы один источник в
`claim_sources`. Ни одно из 19 не удовлетворяет ни тому, ни другому.

Гейт при этом работает: в selftest проверка «существенное утверждение без
подтверждения блокирует выпуск» проходит, и шаг `article_autopublish` зовёт
`factGate` перед выпуском (`lib/seo/steps-article.ts:1017`). То есть механизм
блокировки жив, а подтверждать ему нечем.

**Вывод для планирования:** E2 и E3 — не доработка слоя доказательств, а его
создание с нуля. Оценку это меняет в большую сторону.

## 8. Расхождение файлов миграций и базы

`supabase/migrations/20260908000003_seo_cron.sql` планирует ночные задачи через
`seo.enqueue_nightly(...)`, которая в файле — заглушка, ничего не делающая. При этом
реальное ночное обновление выполняет тик на Vercel собственным списком шагов
(`app/api/seo/tick/route.ts:53`), раз в ~20 часов по отметке
`settings.last_auto_refresh`.

То есть владельцев расписания фактически два: `pg_cron` дёргает тик, а тик сам решает,
что поставить в очередь. PRD инвариант 3 требует одного владельца — при проектировании
E1 это надо развести явно, а не оставлять как есть.

## 9. Числа GSC: сверка

PRD E0.5 требует сверить расхождения между разделами отчётов. Сверено с базой
17 сентября; окно данных в базе — **2026-05-01 … 2026-09-13**.

| Утверждение в отчёте | Записано | В базе сейчас |
|---|---|---|
| `seo-report.md:14,52` — страничный срез | 11 070 кликов / 845 743 показа | **16 189 / 1 311 216** |
| `seo-report.md:52` — уникальных запросов | 13 930 | **15 848** |
| `seo-report.md:58` — запросный срез, клики | 2 853 | **3 456** |
| `seo-status.md:18` — строк запросов | 152 770, окно ~120 дней | **197 915**, окно 136 дней |

Расхождение методики здесь нет — все четыре числа просто устарели: это снимки,
снятые раньше, и **ни у одного не проставлена дата снятия**. Вот это и есть дефект:
число без даты в отчёте неотличимо от числа неверного.

**Структурное расхождение, которое важнее.** Страничный и запросный срезы
несопоставимы: 16 189 кликов против 3 456 на одном и том же окне. Запросный срез
теряет 79% кликов, потому что Google скрывает редкие запросы. Отчёт это
оговаривает (`seo-report.md:58`), и оговорка верна.

**Следствие для KPI:** в итоговые показатели берётся только страничный срез
(`gsc_page_daily`). Запросный годится для разбора запросов и ни для чего больше.
Складывать их нельзя.

Сверка с экраном: «клики за 28 дней = 3 024» на `/admin/seo` совпали с расчётом по
базе за 2026-08-17 … 2026-09-13 точно.

**Дефект найден при этой сверке.** `scripts/seo-selftest.ts` выполняет настоящий
`gsc_import` за один день по боевой базе, и импорт перезаписывает
`settings.gsc_import_health` — сторож, поставленный ловить молчаливую потерю данных
(в комментарии `lib/seo/steps.ts:167` описан случай, когда импорт две недели писал
11 страниц в день вместо 165, и заметили это только по «обвалу трафика»). После
прогона selftest сторож показывал однодневное окно вместо полного.

Обнаружено тем, что я сам запустил baseline-selftest и испортил запись. Исправлено:
проверка теперь снимает значение до импорта и кладёт обратно после
(`scripts/seo-selftest.ts:120`). Испорченная запись восстановится сама при ближайшем
ночном импорте; проверять, что она снова описывает полное окно, — по значению
`gsc_import_health.startDate`.

## 10. Состояние конвейера

19 статей: 7 опубликовано, 5 на просмотре, 2 одобрены, 5 отклонены.
(PRD в разделе 4.6 называл 4 на просмотре — с тех пор прибавилась одна.)

**Причина отклонения не записана ни у одной из пяти.** Механизм есть:
`rejectArticle()` пишет строку в `change_sets` с текстом «отклонено человеком: …»
(`app/admin/seo/articles/actions.ts:133`). В таблице 14 строк, **ни одной строки
отклонения**. Значит статусы проставлены мимо этого пути — вероятнее всего прямым
запросом к базе. Восстановить причины неоткуда.

PRD 4.6 требует «каждое решение с записанной причиной, без массового удаления».
Выполнить это можно только заново: список из пяти статей — в
`docs/implementation-backlog.md`, решение по каждой принимает человек.

**Темы переоткрывались после отклонения.** «как получить грант на обучение в китае»
существует трижды (#2, #5, #8 — все отклонены) и в итоге вышла 11 сентября.
«поступление за границу» — #3 отклонена, #6 сейчас на просмотре. Отклонение темы
не закрывает её для повторной генерации.

**Записи о ревью нет.** Таблица `seo.review_sessions` пуста. То есть база замечаний
по статьям, на которую опирается метрика «число замечаний на статью» из PRD 12,
сейчас не наполняется.

## 11. Найденные дефекты

Отсортированы по тому, что чинить первым.

**Д-1. `article_fix` считает номер версии от текущей, а не от последней.**
`lib/seo/steps-article.ts:647` берёт `version_no` из версии, на которую указывает
`articles.current_version_id`, и прибавляет единицу. Если более поздняя версия уже
есть, вставка падает на `unique (article_id, version_no)`
(`20260908000001_seo_schema.sql:109`). Рядом, в `:846`, тот же расчёт сделан
правильно — через максимум. **9 из 16 упавших задач — это.**

**Д-2. `article_fix` падает на статье без темы.** `:626` читает тему по
`article.topic_id`, при `null` получает `null` и передаёт в `buildContext`, где
читается `topic.primary_keyword` (`:88`). Статьи без темы создаёт ручной путь
(`:835`). **5 из 16 падений.**

**Д-3. Ошибки `article_fix` терминальны без попытки повтора.** У 12 из 16 упавших
`attempts = 0` — значит шаг вернул `failed`, а не `retry`, и `complete_job` закрыл
задачу сразу. Для Д-1 и для 429 от провайдера это неверно: обе ошибки временные.

**Д-4. Эмбеддинги не оплачены.** `voyage 429: You have not yet added your payment
method` — 2 падения. Блокирует проверку каннибализации в починке статьи.

**Д-5. Причина отклонения теряется молча.** Вставка в `change_sets` обёрнута в
`warnOnError` (`actions.ts:136`), который только пишет в консоль
(`lib/supabase/write-guard.ts:37`). Статья отклоняется даже если причина не записалась.

**Д-6. Выбор статьи для автопубликации — по номеру.** `steps-article.ts:1013` —
`.order('id')`. Ни плановой даты, ни приоритета. PRD E1.11.

**Д-7. Время выпуска случайное.** `lib/seo/flow.ts`, `nextPublishAt` — случайный час
внутри окна, с обоснованием «одинаковый час изо дня в день выдаёт машину». Видно по
фактам выпуска: 09:06, 16:58, 15:34, 14:10, 13:46. PRD E1.12 велит планировать по
аудитории.

**Д-8. Три задачи с отменённым исходом «no handler for step».** `jobs` #228–#230 —
след периода, когда обработчика ещё не было. Вреда нет, но при подсчёте статистики
очереди их надо исключать явно.

## 12. Чего нет из того, что нужно PRD

Ничего из перечисленного не существует даже частично:

- схема `content` целиком — пакеты, варианты, публикации, каналы, политики;
- `outbox_events` / `event_receipts` и событийный мост от `article_verify`;
- `runs`, `budget_reservations`, `cost_ledger`;
- `attention_items`, `metrics_daily`, `audit_events`;
- коннекторы Telegram и VK (бот Telegram в CRM есть, но это бот уведомлений,
  не канальный коннектор с `capabilities`/`reconcile`/`fetchMetrics`);
- приёмник атрибуции для форм Tilda — сейчас UTM тянутся только с квиза `/book`;
- экран `/admin/content`.

Из полезного к переиспользованию: `seo.lead_identities` и `seo.attribution_events`
существуют (PRD E5.3 требует не заводить вторую базу — и не надо),
`lib/seo/safe-fetch.ts` закрывает часть требований E6.2.

## 13. Что осталось непроверенным

Честный список — сюда смотреть перед тем, как опираться на этот документ.

1. **Характеристики сервера сайта.** Подключение по SSH заблокировано политикой
   безопасности среды. Известно только из панели Timeweb: 4 ядра, 8 ГБ, 80 ГБ NVMe,
   дата-центр Москва. Для воркеров эта машина не годится независимо от ресурсов —
   из России недоступны API моделей.
2. **Права ролей БД на схему `seo`.** По файлу миграции
   (`20260908000005_seo_grants.sql`) доступ выдан только `service_role`. Что
   применено в базе на самом деле, проверять надо через `information_schema`, а это
   требует прямого SQL-доступа.
3. **Регион проекта Supabase.** Домен закрыт Cloudflare, регион по IP не
   определяется. Нужен для выбора дата-центра воркеров — влияет на задержки.
4. **Резервная копия базы и восстановление.** См. `docs/adr/0004-rezervnoe-kopirovanie.md`.
   _Поправка от 17 сентября:_ dev-окружение существует — отдельный проект
   Supabase в `.env.development.local`. В аудите этого не было, потому что я
   смотрел только `.env.local`. Смотреть надо было все файлы окружения.
5. **Почему пять статей отклонены.** Данных нет, восстановлению не подлежит.
