## Этап 3 — техническая база сайта — код готов, ждёт выкладки

**Поправка к прошлым отчётам.** Утверждение «на сайте нет canonical» — неверное,
оно было сделано по главной странице. Проверено заново, двумя способами:

```bash
curl -sL https://goandstudy.com/postupit-v-yuzhnuyu-koreyu/ | grep -o '<link rel="canonical"[^>]*>'
# → <link rel="canonical" href="https://goandstudy.com/postupit-v-yuzhnuyu-koreyu/" />
```

и по нашей же базе обхода: из 159 страниц **без canonical ровно одна — главная**.
Это ядро WordPress: `rel_canonical()` печатает self-canonical на singular, но не
на главной и не на архивах. Плагин тут ни при чём.

Что действительно отсутствует:

| Дырка | Масштаб | Чем закрывается |
|---|---|---|
| JSON-LD | **83 из 159** страниц, включая все важные | мост v0.3 + `seo-apply-schema.ts` |
| canonical на главной и архивах | 1 страница + архивы | мост v0.3 |
| meta description | 3 страницы | мост v0.3 (мета уже пишется) |

То есть приоритет — не canonical, а **разметка**. Ставить Rank Math ради одного
тега на главной незачем; вариант 1 (расширить мост) остаётся верным решением, но
по другой причине, чем предполагалось.

Написан **мост v0.3**, `wp-bridge/goandstudy-seo-bridge.php`, синтаксис проверен
(`php -l` в контейнере php:8.2). Что изменилось:

| Изменение | Зачем |
|---|---|
| JSON-LD и description печатаются по мете, без требования `_gs_seo_key` | **главное**: применять разметку к страницам, которые создавали не мы |
| **новый `GET /resolve?url=`** | публичный URL → ID поста; без этого CRM не знает, какой пост править — у чужих страниц нет меты `_gs_seo_key` |
| canonical на всех индексируемых URL: главная, архивы, пагинация | закрыть то, что не делает ядро |
| `remove_action('wp_head', 'rel_canonical')` | ядро печатает свой canonical на singular — иначе будет два тега |
| JSON-LD валидируется через `json_decode` перед печатью | битая мета не сломает страницу |
| Отбой, если появится Yoast / Rank Math / AIOSEO / SEOPress | не задвоить canonical |
| Аварийный выключатель `define('GS_SEO_DISABLE_HEAD', true)` | откат без правки файлов |
| `/export?post_type=page\|any` | инвентарь не только постов |
| мета регистрируется и для `page` | страницы — большая часть сайта |

Выкладка: положить файл в `wp-content/mu-plugins/` поверх v0.2. Правок nginx и
`wp-config.php` не требует. Откат — вернуть v0.2 из `/root/backups/`.

Проверка после выкладки — на любой внутренней странице должен остаться **ровно
один** canonical (не ноль и не два):

```bash
curl -sL https://goandstudy.com/stipendii/ | grep -c 'rel="canonical"'   # ожидается 1
curl -sL https://goandstudy.com/ | grep -c 'rel="canonical"'             # было 0, станет 1
```

# Дополнение от 09.09.2026, вечер: конвейер производства и находка по canonical

## Найдено при подготовке первой статьи

**1. Инвентарь был неполным — 61 страница мимо.** Он строился по `sitemap.xml`, а
sitemap на сайте неполный. Живые страницы, которых модуль не видел, собрали
**151 516 показов** за 90 дней — среди них самые посещаемые страницы сайта.
Исправлено: `scripts/seo-inventory-from-gsc.ts --apply` добрал 51 страницу
(10 из 61 отдают 404/410 — это отдельная задача на редиректы). Инвентарь: 159 → 220.

**2. Поправка к первой редакции этого раздела.** Сначала здесь было написано, что у 50
страниц canonical указывает на другую страницу. **Это неверно.** Ошибка вышла из проверки
через `curl -sL`: флаг `-L` молча идёт по редиректу, и canonical снимался уже со страницы
назначения.

Проверка без перехода по редиректам показала другое:

```bash
curl -s -o /dev/null -w '%{http_code} → %{redirect_url}' https://goandstudy.com/magistratura-v-avstrii
# → 301 → https://goandstudy.com/postupit-v-avstriyu/
```

Из 50 «страниц с чужим canonical» **редиректят все 50**, страниц с 200 и чужим canonical —
ноль. То есть подстраницы стран когда-то склеили в хабы через 301. Это осознанное
действие, а не поломка.

Что при этом остаётся настоящей проблемой: по этим URL до сих пор идут показы
(150 305 за 90 дней), и конкретный запрос — «магистратура в Австрии», «гранты в США» —
приземляется на общую страницу страны, которая на него не отвечает. Отсюда и позиции
30–50. Решается либо отдельными страницами под подтемы, либо тем, что хаб начинает
отвечать на подзапросы. **Это и есть первая настоящая работа для машины статей.**

Заодно исправлена находка: краулер ходит по редиректам и кладёт в `url` конечный адрес,
а canonical читает уже со страницы назначения — поэтому любой редирект выдавался за
`canonical_mismatch`. Теперь редирект классифицируется отдельно
(`redirected_with_traffic`). После пересчёта: 50 редиректов с трафиком и 10 настоящих
критических (404/410) вместо прежних 60 в одной куче.

Вопрос владельцу остаётся, но другой: склейка подстраниц в хабы была осознанной или
это наследство? От ответа зависит, писать ли под эти запросы отдельные страницы.

## Калибровка на живых статьях (§16.5)

`npx tsx scripts/seo-standard-check.ts 10` — прогон стандарта по существующим статьям
блога. Смысл проверки прямо из §16.5: если статьи редактора массово не проходят порог,
неверен порог, а не статьи. Результат по 10 статьям:

| Требование | Не проходит | Разбор |
|---|---:|---|
| 4.1.5 TOC при 4+ H2 | 100% | оглавлений в блоге нет вообще — новое требование, порог оставлен |
| 4.3.4 «Читайте также» 3–5 ссылок | 100% | блока нет ни в одной статье — новое требование |
| 8.1 3–8 внутренних ссылок | 90% | реальная дыра: в статьях блога ноль контекстных ссылок (отсюда же 13 сирот в находках) |
| 2.1 title 50–60 | 80% | реальная дыра, см. ниже |
| 2.6 description 140–160 | 70% | реальная дыра, совпадает с находкой `title_length` |
| 6.1 длинные тире | было 90%, стало 40% | **ошибка была в моей реализации**, см. ниже |

Два вывода из калибровки:

**1. Тире считались неправильно.** §6.1 выводит из-под правила тире в роли сказуемого
(«Bocconi — частный университет»), а я считал все подряд — и заваливал 90% живых статей,
написанных людьми. Морфологии здесь нет, но у сказуемого есть свойство: оно одно на
предложение, а машинный почерк — это несколько тире в одном предложении. Теперь считаются
только «лишние» тире сверх одного на предложение. Провал упал до 40% — это уже похоже
на правду.

**2. Тема дописывает бренд в title.** Проверено на живых страницах:

```bash
curl -sL https://goandstudy.com/blog/chto-takoe-pdh/ | grep -oE '<title>[^<]*'
# → PhD — что это за степень, расшифровка и как поступить – Go and Study
```

H1 короткий, а в `<title>` тема добавляет « – Go and Study» — 15 символов. Значит бюджет
автора не 60 символов, а 50, иначе в выдаче заголовок обрежется. Это и есть причина
находки «54 страницы с проблемным title». Учтено и в проверке, и в промпте генератора.

## Что проверено без ключа к модели

- Лимиты темпа публикаций — считаются по `change_sets`, сейчас «в норме».
- План входящих ссылок — на живых страницах находит 2 из 2 нужных мест вставки
  с конкретными предложениями, куда встаёт ссылка.
- По дороге нашлись и исправлены две ошибки: в план попадала одна и та же страница
  пять раз (в инвентаре несколько `normalized_url` ведут на один живой URL — следствие
  тех самых 301), и в доноры лезли страницы, которые сами редиректят.

2. **`WP_BRIDGE_SECRET`** — без него не работает публикация и не выложить мост v0.4.
3. Ответ по 301-склейке: писать ли отдельные страницы под подзапросы.
4. Решения из §16 приложения F: изображения, страница автора, словарь терминов.
