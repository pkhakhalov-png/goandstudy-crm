# Бэкапы: что есть, где лежит, как восстановить

Состояние на 17 сентября 2026 года.

---

## Что было до сегодняшнего дня

Проверил в панели Supabase, а не по памяти:

- база CRM бэкапилась **ежедневно, хранение 8 дней**;
- **PITR выключен** — восстановиться на произвольную минуту нельзя;
- **файлы хранилища в бэкап не входят** — Supabase пишет это прямым текстом:
  в базе лежат только записи о файлах, сами файлы отдельно;
- **сайт goandstudy.com не бэкапился вообще** — ни дампа MySQL, ни копии
  `wp-content` на сервере не было.

То есть договоры клиентов и весь сайт держались на честном слове.

---

## Что настроено

Ночью в **03:30 по Москве** на сервере сайта (Timeweb, Москва) запускается
`/usr/local/bin/gs-backup.sh`. Копия ложится не туда же, где оригинал, и это
главное: база CRM живёт в Supabase, файлы там же, сайт — на этом сервере.

| Что | Откуда | Как часто |
|---|---|---|
| Данные CRM: 94 таблицы | CRM по подписанному запросу | каждую ночь |
| Файлы клиентов: 2191 объект | хранилище Supabase | каждую ночь, докачиваются изменения |
| Выгрузки Search Console | те же таблицы | по воскресеньям |
| База сайта | mysqldump | каждую ночь |
| Файлы сайта (`wp-content` с темой) | tar | каждую ночь |

Хранение — **30 дней**, дальше старые копии удаляются.

### Почему на сервере нет ключей Supabase

Сервисный ключ даёт полный доступ к CRM **на запись**. Положи мы его на сервер
сайта — взлом сайта означал бы взлом всей системы. Поэтому наоборот: сервер
ничего не знает и только просит, а решает CRM. Запрос подписан отдельным
секретом, действует пять минут и работает только на чтение.

### Почему файлы лежат зеркалом

Первый прогон весил 5,4 ГБ: две тысячи файлов качались целиком. Тридцать таких
копий — 162 ГБ при 71 свободном, то есть через две недели диск кончился бы и
бэкапы встали бы молча.

Теперь файлы лежат одним зеркалом (`files-mirror`), докачиваются только при
расхождении размера, а ночная копия — жёсткие ссылки на него. Неизменившийся
файл занимает место один раз, но виден во всех копиях.

**Цена в цифрах:** вся история сейчас 5,4 ГБ, из них 5,3 — зеркало. Каждая
следующая ночь стоит около **130 МБ**. Тридцать дней — примерно 10 ГБ при 65
свободных.

## Где лежит

```
/root/backups/gs/
├── files-mirror/              зеркало файлов хранилища
├── 2026-09-17/
│   ├── tables/                данные CRM: <схема>.<таблица>.jsonl.gz
│   ├── files/                 жёсткие ссылки на зеркало
│   ├── wordpress-db.sql.gz    база сайта
│   ├── wordpress-content.tar.gz
│   ├── manifest.json          что выгружалось
│   └── README.txt
└── …
```

Настройки — `/etc/gs-backup.env` (права 600): адрес CRM, общий секрет, срок
хранения. Журнал — `/var/log/gs-backup.log`.

## Как восстановить

**Одна таблица.** Данные лежат построчным JSON:

```bash
zcat /root/backups/gs/2026-09-17/tables/public.clients.jsonl.gz | head
```

Залить обратно — через PostgREST или SQL-редактор, по строкам. Структура базы
(таблицы, функции, политики) в бэкапе не хранится: она лежит в миграциях
репозитория и накатывается оттуда.

**Файл клиента.** Просто лежит на месте:

```bash
ls /root/backups/gs/2026-09-17/files/client-docs/
```

**Сайт.**

```bash
zcat /root/backups/gs/2026-09-17/wordpress-db.sql.gz | mysql -u USER -p wordpress_db
tar -xzf /root/backups/gs/2026-09-17/wordpress-content.tar.gz -C /var/www/html/wordpress/
```

**База CRM целиком** — быстрее из штатного бэкапа Supabase (панель → Database →
Backups → Restore), он физический и восстанавливает структуру вместе с данными.
Наша копия нужна там, где штатный не поможет: файлы хранилища, срок больше
восьми дней, потеря доступа к самому Supabase.

## Чего эта схема не делает

- **Не хранит структуру базы CRM.** Она в гите, и это осознанно — дублировать
  то, что уже версионируется, незачем.
- **Не шифрует копии.** Они лежат на сервере под root. Если нужно хранить их
  где-то ещё, шифрование придётся добавить.
- **Не увозит копии с этого сервера.** Пожар в одном датацентре переживёт база
  CRM, но не эта история. Следующий разумный шаг — отгружать архивы ещё и в
  объектное хранилище.
- **Не бэкапит секреты.** Ключи и токены живут в Vercel и на ноутбуке; при
  потере доступа к Vercel восстанавливать их будет неоткуда.
