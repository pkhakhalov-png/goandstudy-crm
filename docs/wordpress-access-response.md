## 3. REST — почему не открыт

### Найдено при осмотре

Сайт был скомпрометирован, вектор — REST API:

- **19.07–25.08.2026** — создано 78 администраторов
- **в ночь 26→27.08.2026** — ещё 5
- механизм: `POST /?rest_route=/batch/v1`

Источник: комментарии в `/etc/nginx/conf.d/wordpress.conf` и в `gs-security.php`.

**База сейчас чистая:** в `wp_users` один пользователь `admin` (2022-12-11,
gs@goandstudy.com). Зачистка выполнена.

Действующая защита закрывает все три пути к API:

| Путь | Защита |
|---|---|
| `/wp-json/` | allowlist 92.241.87.90 + basic-auth |
| `/index.php/wp-json` | allowlist + basic-auth |
| `?rest_route=` | 403 для всех, кроме 92.241.87.90 |
| уровень приложения | `gs-security.php` — REST только авторизованным |

То есть basic-auth здесь — **не рутинная защита, а реагирование на инцидент**.
Снимать его с `/wp-json/` целиком означало бы вернуть ту самую дверь.

### Блокер, о котором бриф не знает

`gs-security.php` отклоняет REST для неавторизованных через фильтр
`rest_authentication_errors`. Этот фильтр отрабатывает **раньше**, чем
`permission_callback` моста, поэтому HMAC-проверка не успевает выполниться.

Следствие: проверка из шага 3 брифа вернёт **не** ожидаемый `gs_auth`,
а `rest_not_logged_in` — даже если открыть nginx.

### Что предлагаю сделать

1. **nginx:** открыть не `/wp-json/`, а только `/wp-json/goandstudy-seo/`.
   Это ровно то, что просит бриф в пункте 3. Namespace защищён HMAC внутри моста.
   `wp/v2`, `batch/v1`, `?rest_route=` остаются закрыты.
2. **gs-security.php:** добавить исключение для namespace `goandstudy-seo/v1`,
   чтобы запрос доходил до HMAC-проверки. Общая защита не ослабевает.

Инвентарь через `wp/v2` открывать не нужно — у моста есть свой `/export`.

## Замечание к архитектуре

В nginx стоит allowlist на `92.241.87.90`. CRM живёт на Vercel, у него исходящие
IP плавающие — на allowlist рассчитывать нельзя. Единственной защитой моста
будет HMAC, это стоит учесть при настройке.

## Замечания по коду моста

Не блокеры, но до продакшена:

1. `/redirects` принимает `to_url` без валидации и ставит 301 куда угодно.
   Под HMAC, снаружи не эксплуатируется, но при утечке секрета — готовый
   инструмент угона трафика. Ограничить редиректы своим доменом.
2. `gs_seo_log` выполняет `CREATE TABLE IF NOT EXISTS` при каждой записи —
   лишний запрос на каждую операцию. Вынести в разовую инициализацию.

## Требуются три разрешения

1. Правка `wp-config.php` — вписать секрет
2. Правка nginx — открыть `/wp-json/goandstudy-seo/`
3. Правка `gs-security.php` — исключение для namespace моста

После них прогоняю проверку: `lookup` должен ответить `gs_auth` 401
(подпись отсутствует) — это признак живого моста.
